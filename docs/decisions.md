# 决策与实验记录

## 实验1：NL2SQL 的表名问题（2026-09-10）

### 问题

用户问："张三打回超过3次的项目有哪些"

### 版本A：无字段说明

- 生成SQL：`SELECT ... FROM project_table WHERE ...`
- 结果：SQL 执行报错（表名 project_table 不存在）
- 结论：模型知道列名，但不知道表名，自己瞎猜

### 版本B：加上字段说明

- 生成SQL：`SELECT ... FROM projects WHERE owner = '张三' AND reject_count > 3`
- 结果：SQL 正确，返回空
- 结论：空是因为数据里没有"张三"这个人，SQL 是对的

### 学到的

1. prompt 里只有列名不够，要加"字段语义说明"
2. 空结果有两种可能：SQL错了 / 数据里真的没有
3. 不能自动对空结果重试，会误伤"真的没有"的情况

## 实验2：表名缺失对 NL2SQL 稳定性的影响（2026-09-10）

### 背景

Golden Set 15 题首次跑完，结果 15/15 通过，但只有 7/15 一次通过，
其余 8 题靠自修正兜底。观察发现：8 次重试全部是"表名猜错"或
由"猜表名"引发的思考泄漏。

### 根因

SYSTEM_PROMPT 里给了表结构（列名+类型+说明），但没有给表名。
模型不知道列属于哪张表，只能每次猜，猜出过：

- project_table
- project
- project_name
- 表名（字面量）

### 修复

在 SYSTEM_PROMPT 中显式加入 "表名：{table_name}"，并在
generate_sql / fix_sql 中传入。

### 结果对比

| 版本   | 通过  | 一次通过 | 重试次数 |
| ------ | ----- | -------- | -------- |
| 修复前 | 15/15 | 7/15     | 8        |
| 修复后 | 15/15 | 15/15    | 0        |

### 意外收获

思考泄漏（`Wait, I need to check...`）也一并消失。推测原因：
模型之前需要"思考表名"，思考过程混入输出；表名给定后，
无需犹豫，输出自然干净。

### 学到

1. prompt 缺关键信息，模型会用"猜"来补，且每次猜法不同
2. 症状（输出污染）和根因（信息缺失）常常不在同一层
3. 自修正机制的正确位置是"兜底"，不是"主力"。一次通过率
   才是系统健康度的核心指标

## 实验3：改写器的"过度改写"问题（2026-09-10）

### 背景

多轮对话加入改写器后，测试三个场景：

- 首轮：张三负责的项目有几个？
- 追问：那李四呢？
- 独立：打回次数最多的项目是哪个？

### 问题

第三句被错误改写成"张三负责的项目中打回次数最多的项目是哪个？"
—— 添加了历史里的人名，悄悄改变了问题范围。

### 为什么危险

- 漏改 → SQL 报错或答非所问 → 容易发现
- 过度改 → 悄悄改了语义 → 结果看起来合理 → 极难发现

### 根因

模型分不清"省略"和"独立"。看到历史里有"张三"，
看到当前问题没提具体人名，就"好心"地把人名补了进去。

### 修复

在 prompt 里：

1. 加原则："不确定就原样返回，宁可漏改，不可过度改写"
2. 加三个 few-shot 示例：该改 / 不该改 / 指代明确
3. 加兜底：结果包含换行时只取第一行

### 结果

三个场景全部正确。

### 学到

改写器最大的风险不是"改得不够"，而是"改得太多"。

## 实验4：多轮对话完整测试（2026-09-10）

### 测试场景

连续五轮对话，考察改写器的判断能力。

### 结果

| 轮次 | 问题                       | 改写                     | 结果 |
| ---- | -------------------------- | ------------------------ | ---- |
| 1    | 张三负责的项目有几个？     | 无（首轮）               | ✅   |
| 2    | 那李四呢？                 | → 李四负责的项目有几个？ | ✅   |
| 3    | 那打回次数最多的项目是哪个 | 无（语义完整）           | ✅   |
| 4    | 已下证的项目有哪些？       | 无（独立）               | ✅   |
| 5    | 那待提交的呢?              | → 待提交的项目有哪些？   | ✅   |

### 关键观察

- 第3句带"那"字但语义完整 → 改写器正确判断为"不改"
- 第2、5句是真指代 → 改写器正确补全
- 改写器的"保守策略"（不确定就原样返回）生效

### 学到

改写器需要同时具备两种能力：

1. 识别真正的指代（补全）
2. 识别伪指代（原样返回）
   两者中，"不误改"比"能改对"更重要。

## 实验5：自修正机制的"洗白"漏洞（2026-09-10）

### 背景

用户问"你把项目A删掉"，系统返回"没有找到符合条件的数据"。

### 现象

- 生成的 SQL：SELECT \* FROM projects WHERE project_name = '项目A'
- 用户要求的是 DELETE
- 系统没删，只是查了一下，还返回了"没找到"
- error 字段是 null，看起来一切正常

### 根因

1. 模型生成了 DELETE
2. execute.py 的护栏拒绝执行
3. **自修正机制把"拒绝"当成"可修复错误"，生成了 SELECT 来"通过检查"**
4. 用户意图被悄悄篡改

### 为什么危险

- 用户以为"项目A不存在"，实际是"我没删，只查了"
- 自修正机制会自动把非法操作"洗白"成合法操作
- **这是安全漏洞，不是普通 bug**

### 修复

1. 新建 guard.py：独立判断 SQL 是否为写操作
2. 在 generate_sql_with_retry 的**两个位置**做安全检查：
   - 初次生成后
   - 每次 fix_sql 后（防止洗白）
3. 写操作直接抛 SecurityError，**不进入自修正**
4. execute.py 保留护栏，作为深度防御

### 学到

1. 自修正机制必须有边界：**安全拒绝 ≠ 可修复错误**
2. guard 必须是独立模块，和执行分离
3. 检查点要放在"修正前后"两处，不能只在入口


## 实验6：编排层——意图判断的引入（2026-09-10）

### 背景

用户输入"全没用了"，系统生成了错误 SQL，硬答了结果。

### 问题

模型不知道"什么时候该答、什么时候该问"，默认一切输入都要翻译成 SQL。

### 修复

新建 intent.py，做四分类：

- QUERY：明确查询
- CLARIFY：意图模糊，反问
- CHITCHAT：闲聊
- UNSUPPORTED：写操作或不支持

设计：

1. 规则先行（写操作关键词直接拒）
2. LLM 兜底（判断剩下的）
3. 两行协议（第一行标签，第二行内容）
4. 失败兜底为 QUERY（宁可走错，不可卡住）

### 结果

模拟"想删数据库"场景，连续输入"没用"、"废弃"、"清空"、"数据库"，
系统全部正确识别为 CLARIFY 并反问，未生成任何错误 SQL。

### 已知遗留问题

CLARIFY 追问后，用户的回答不会被当作追问的延续（classify 无状态）。
例如："清空" → 系统问"清空什么" → 用户答"数据库" →
系统当成新问题反问，而不是理解成"清空数据库"。
优先级：低（体验问题，不危险）。


## 实验7：代码规范化与路径重构（2026-09-10）

### 背景
上传 GitHub 前做代码审查，发现两类问题：
1. load_config 在三个文件里重复
2. 所有路径依赖 CWD，从别的目录跑会崩

### 修复
1. 新建 config.py，提供 PROJECT_ROOT 和 load_config（唯一来源）
2. 新增 resolve() 函数，统一处理相对路径 → 绝对路径
3. main.py / run_eval.py 里，db_path 只算一次，后面复用
4. nl2sql.py 的重试 print 改为 logging.warning

### 验证
- 从项目根跑：通过
- 从 src/ 跑：通过
- 评测：15/15

### 学到
1. 重构最容易翻车的地方：函数返回值含义变了，调用方要全改
2. 路径不要"到处拼"，要"拼一次，到处用"
3. 一次只改一个文件，改完立刻验证——小步快跑
