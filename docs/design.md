# 零 · 全局约束

> **这一章是闸门。** 它没定完，后面每一层都在猜。
> 它只有一个来源：**本地 · 单用户 · 单实例。**

## 一、这个前提废掉了什么

PostgreSQL、向量数据库——它们的核心卖点全在**规模**和**多用户**上：

| 卖点 | 我们的情况 |
|---|---|
| 多连接并发 | 一个人 |
| 网络访问 | 同一台机器 |
| 多用户权限体系 | 一个用户 |
| 水平扩展 · 分片 | 数据几万行 |
| ANN 索引（HNSW/IVF） | 几千条，暴力算就是最优解 |

**这些卖点一条都用不上，成本却要全付。** 而数据库的成本不是"买了多少钱"，是**多一个进程、多一个端口、多一个密码、多一份要备份的东西、多一处会崩的地方**。

**所以：数据层不需要"服务器"这个形态。**

## 二、十项定案

| # | 项 | 定案 | 体积 | 理由 |
|---|---|---|---|---|
| 1 | **数据源** | **SQLite 单文件** | 0 | 标准库自带；备份 = 复制一个文件 |
| 2 | **向量** | SQLite 存向量 BLOB + **FAISS 索引** | 15.5 MB | 见第三节 |
| 3 | **软删除隔离** | **视图** | — | SQLite 没有 RLS，退回视图 |
| 4 | **交付形态** | **文件夹 + Inno Setup 安装包** | — | Python 依赖多，单 exe 每次要解压到临时目录，启动慢且易被杀软拦 |
| 5 | **装到哪** | 默认 `%LOCALAPPDATA%`，**可自定义路径** | — | 不弹 UAC；且安装目录必须用户可写（`data/` 在里面） |
| 6 | **浏览器内核** | **不内置**，借系统 WebView2 | ~5 MB | 省 500MB+；两者都是 Chromium，渲染无差 |
| 7 | **网络依赖** | **只有 LLM API** | — | 实测确认，全项目无其他外连 |
| 8 | **RAG · embedding** | `bge-small-zh-v1.5`，**随包** | 91 MB | 中文够用，最小可用档 |
| 9 | **RAG · reranker** | `gte-multilingual-reranker-base`，**留接口、按需下** | (584 MB) | 中文 reranker 的现实最低价 |
| 10 | **RAG · 关键词召回** | **不做** | — | SQLite 无开箱中文分词（trigram 最少 3 字） |
| 11 | **平台** | **Windows 优先，接口不焊死** | — | 见第四节 |

**包体：约 465 MB。**

```
Python 依赖（去掉 playwright）        243 MB
Python 解释器                        ~100 MB
pywebview + pythonnet + WebView2       ~15 MB
SQLite                                  ~0 MB
FAISS                                  15.5 MB
RAG embedding（bge-small-zh）           91 MB
────────────────────────────────────────────
约 465 MB
```

## 三、向量为什么不是一个"库"

**"向量库"这个词让人以为它是"一个放切片的柜子"。它不是。**

一个向量库通常捆三样东西，而这三样可以拆开：

| 东西 | 是什么 | 该谁存 | 能不能重来 |
|---|---|---|---|
| **切片原文** | 文本 | **SQLite 的 TEXT 列** | **不能**——丢了就是丢了 |
| **向量** | float32 数组 | **SQLite 的 BLOB 列** | 能（原文 + 模型重算） |
| **索引** | HNSW/IVF 那套加速结构 | **FAISS** | **能**——拿原文重算一遍就有 |

**检索流程：**

```
问题 → embedding → FAISS：「哪几条最像？」→ 只还回 ID（3, 17, 42）
     → 回 SQLite：SELECT text FROM chunks WHERE id IN (3,17,42) → 拿到切片
```

**为什么必须这么拆：** 切片是**真数据**（唯一真源、要事务、要原子），索引是**派生数据**（丢了无所谓）。捆在一起的做法——删一份文档要同时删两处，**跨存储没有事务**，迟早出现"记录删了但切片还在，检索还能捞出来"。

拆开之后：**删文档只删 SQLite（一个事务），索引下次重建自然就不含它了。永远对不上，因为能对上的只有一份。**

**架构约束（不可违反）：SQLite 永远是唯一真源，FAISS 永远是派生索引。任何写操作只写 SQLite，索引只在启动时或数据变更后重建。**

## 四、为什么不上 PG

PG 我们能跑起来（实测过：`postgres:16` 裁到 `bin/lib/share` 只有 120MB），**但裁不掉的是它的形态：一个要起、要停、要占端口、要设密码、要备份目录树、崩溃了会残留的进程。**

**而它换来的 RLS，是这一整套里唯一真正的损失。**

| | PG | SQLite |
|---|---|---|
| 软删隔离 | **RLS**（数据库层面强制） | 退回**视图** |
| 进程 | +1 | 0 |
| 首次使用 | initdb + 建库 + 设密码 | 打开一个文件 |
| 备份 | 目录树 / `pg_dump` | **复制一个文件** |
| Windows 管理员坑 | **PG 拒绝以管理员身份运行** | 无 |

**判断：这个项目的威胁模型是「工具自己写错」，不是「恶意用户绕过权限」。RLS 在单用户本地场景里是过度设计。** 用视图换掉一个常驻进程，划得来。

## 五、RAG 的边界（预埋）

RAG 排在第四个阶段。这一节只锁三件，防止后面反复：

1. **embedding 随包**（91MB）——它是命脉，没有它整条链跑不起来
2. **reranker 留接口、权重按需**——它是质量增强，没有它链路照样完整
3. **关键词那一路不做**——SQLite 的中文分词是断的，别指望它。**召回质量由 embedding + reranker 负责**

**规模边界（判据）**：全量读向量 + 算一次余弦，**几十毫秒以内就继续暴力；超过几百毫秒**才上 ANN。换的时候只换索引那一层，切片一个字不动。

## 六、平台：Windows 优先，但接口不焊死

**今天只做 Windows，这是明确的。** 但"只做 Windows"和"写死 Windows"是两件事。

### 为什么不是"焊死"

内核的选择（第 6 项）本身**就是跨平台的思路**——**不打包浏览器，用系统自带的那个**：

| | 系统内核 | 来源 |
|---|---|---|
| Windows | **WebView2** | 预装（Win11 100%；Win10 随 Edge 更新分发） |
| macOS | **WKWebView** | 系统自带 |
| Linux | WebKitGTK | 多数发行版有 |

`pywebview` 就是这三者的同一套 API（`edgechromium` / `cocoa` / `gtk`）。**换平台 = 换后端，前端不动。**

### 实测：整个项目的 Windows 绑定只有三处

| 位置 | 现状 | 代价 |
|---|---|---|
| `services/report/charts.py:15` | `["Microsoft YaHei", "SimHei"]` | 补两个字体名 |
| 数据目录路径 | 硬写 `%LOCALAPPDATA%` | 换 `platformdirs` |
| `desktop.py` | `webview.start(gui="qt")` | 改成 auto |

**前端的字体链早就跨平台了**——`splash.css` 里连 Linux 的 `DejaVu Sans Mono` 都列了（那是参考项目的底子）。

**三条加起来不到十行，决定了三年后还能不能上 mac。**

### 另外两件事已经确认

- **PDF 预览**：QtWebEngine **显示不了**（PySide6 6.12 实测，`PdfViewerEnabled` 枚举存在但渲染空白——那份构建没编进 PDFium）。**WebView2 有内置查看器**，这条顺带解决。
- **开机动画那个「按任意键」**：卡的是 Chromium 的 autoplay policy。WebView2 可以用 `--autoplay-policy=no-user-gesture-required` 关掉，**那个闸门在桌面版可以整个删掉**。

# 数据层

> ⚠️ **本章已被「零 · 全局约束」推翻，待重写。**
> 尤其第一节「只对 PostgreSQL 说话」和第四章「软删除用 RLS」——
> 它们都建立在"数据源是个服务器"这个前提上，而那个前提已经不成立了。

## 一、定位

数据层是 **Agent 面对的世界**。它只管「存取」与「理解结构」，不含业务规则。

**只对 PostgreSQL 说话。** DuckDB 已弃用（历史包袱，为兼容它引入了大量分支）。

## 二、表定义 —— 一等概念

一张表的定义，是数据层的地基。**真源在库里**，分两半：

| 内容 | 来源 |
|---|---|
| 列 · 类型 · 必填 · 默认值 · 主键 · 唯一约束 · 外键 | **PG 原生**（`information_schema` / `pg_constraint`），直接读 |
| 表中文名 · 字段中文说明 · 逻辑关系 | **库里 meta 表** |

**一次写（建表时），之后全是读。** 没有硬编码、没有 JSON 文件、没有第二份。

字段的中文说明不是短标签，而是**给 LLM 读的整句解释**——要讲清「这列是什么、什么场合用」。

## 三、表从哪来 —— 两条入口

| 入口 | 怎么来 |
|---|---|
| **对话造** | 自然语言建表、加列、定义关系 |
| **Excel 灌** | 从文件推断结构 |

两条入口都要 **「推测 + 向用户核实」**：

- 上传 Excel 时，Agent 先推测「这可能是库里的哪张表」，再问用户
- 建表时，Agent 先推测「它与别的表有没有关联」，再问用户
- **即使推测「无关联」，也要问** —— 把自己的判断摊给用户，防漏判

## 四、数据的删除与恢复

**软删除：**

- `is_deleted` 标记 —— **行不动**，留在原表
- **RLS 隔离**（不再是视图）—— 一张表只有**一个名字**，砍掉 `视图 / 真实表 _all` 的双名约定
  - 必须 `FORCE ROW LEVEL SECURITY`，否则表 owner 绕过策略
  - SELECT / INSERT / UPDATE / DELETE **各有策略**，缺一则被拒
  - 「恢复」和「清理」要能看见已删行 → 走**特权旁路**
- **定时清理** —— 超期（7 天）物理删除

**前端「数据垃圾桶」：**

- 展示全库所有被软删的行（**跨表**，走特权旁路读）
- 点某行 → 恢复

## 五、结构的回溯

**破坏性操作，动手前先落「整表快照」。**

- 快照 = **那一刻的结构 + 数据**
  （结构回滚必须连数据，否则列回滚后数据成孤儿）
- **一个粒度打天下**：覆盖（重复导入）/ 删表 / 删列 —— 全是整表快照
- 快照**存库里**
- 前端给一个**「版本历史」**面板：选时间点，整体回滚
- 它与「数据垃圾桶」是**两个入口**——一个装行，一个装结构快照

「删一行」不走快照，走软删除。

## 六、关系

- **逻辑关联，不是外键** —— 它陈述的是**事实**（「这两列说的是同一件事」），不是**约束**
- 最小单位是**字段 ↔ 字段**：
  `流水表.customer_id ↔ 客户表.id`
- 附带**基数**（1:N / M:N）
- 存在 **meta 表**里

（外键是「规则」，会被数据库强制；逻辑关联是「事实」，不强制。Excel 灌进来的数据脏，外键多半建不起来，所以用逻辑关联。）

## 七、唯一约束

「什么不能重复」**不需要新概念** —— 它就是**结构**的一部分：

- 建表时给该唯一的列加 **PG 的 `UNIQUE` 约束**
- 归结构 → 原生读
- 数据库层面就挡住重复（**比代码判断可靠**，并发也拦得住）

## 八、重复导入

- **直接覆盖**
- 覆盖前落整表快照 → 7 天内可恢复

# 工具层

## 一、定位

工具是 **Agent 的手** —— 用来达成用户请求的动作。

**核心原则：工具返回，只给「模型」，不给「用户」。**
给用户看的（确认卡片、产物）走另一条路。现在项目把两者混了（`summarize` 那段话既当给模型的结果、又当给用户的答案），所以模型拿到的是"成品文字"、没法接着用。

## 二、工具清单（18 个动作）

| 组 | 工具 |
|---|---|
| **对行** | 查询 · 新增 · 赋值 · 规则重塑 · 删除 · 恢复 · 列出已删 |
| **对表** | 建表 · 加列 · 改列 · 删列 · 删表 · 列出历史 · 回滚版本 |
| **文件** | 导入 · 导出 |
| **产出** | 生成报告 |
| **交互** | 问用户（`ask_user`）—— 发起一次「中断」 |

**`ask_user` 一具体，两用途**（覆盖原来的 A1 / A2）：

```
参数：ask_user(question: string, options?: string[])   // options 建议 ≤3
返回：{ ok: true, answer: "用户选的，或自己打的" }       // 中断后，续跑时才给
```

- **给了 `options`** → 让用户选方向（A2）
- **没给 `options`** → 纯澄清（A1）
- **自由输入框永远在** —— 选项是省事，不是限制

**展示形态**：**底部弹窗**（问题 + 待选项按钮 + 自由输入框）。

**与确认卡片的区别**：都是「中断」，但呈现不同 —— `ask_user` 是弹窗（问答），确认卡片是对话流里的卡片（确认）。**两种中断，两种长相，底下同一条路。**
| **挂起** | 一致性检查（太薄弱，重做中） |

注意区分层级：
- 「关系」不是工具，是**数据**（在表定义里）
- 「RAG」不是工具，是**子系统**（其中的「检索」才是动作）
- 「查看表结构」不是工具，是**上下文**（Agent 总是看得见）

## 三、归类（按性质）

**归类的目的不是减少数量，是给每类定同一套规矩。**

| 类 | 工具 | 规矩 |
|---|---|---|
| **读** | 查询 · 列出已删 · 列出历史 | 幂等、不用确认、返回数据 |
| **写** | 新增 · 修改 · 删除 · 恢复 · 导入 | 要确认 + 走业务规则 + 事务 |
| **结构** | 建表 · 加列 · 改列 · 删列 · 删表 · 回滚版本 | 要确认 + 先落快照 |
| **产出** | 导出 · 生成报告 | 读数据 + 落文件，不改数据 |

同类不必同一个工具（确认形态差异大的分开），但**同类守同一个规矩**。

## 四、返回格式

### 统一原则

- 返回是 **JSON**，只给模型
- **成败看 `ok`**，不看"有没有某个键"（旧代码 `_is_success` 靠猜，把 `not_found` 判成成功）
- **值参数化**（防注入）；**表名 / 列名只能拼，但必须过「表定义」白名单**（标识符没法参数化，是注入的另一条路）
- **多步操作要事务**（单条 SQL 本身原子；只有多步才需要）
- **失败不写"建议"** —— 工具报告事实，不替模型想下一步

### 读类返回

```json
// 成功
{ "ok": true, "status": "ok" | "empty",
  "table": "projects",
  "columns": [...], "rows": [[...]],      // 二维数组 + 列名数组（省 token）
  "row_count": 2, "truncated": false,
  "sql": "SELECT ..." }

// 失败（所有工具通用，形状一致）
{ "ok": false, "error": "...", "error_type": "...", "sql": "..." }
```

- `status: "empty"` = 执行成功但没数据（**不是失败**，但和"有数据"分开）
- 大数据：给前 N 行 + `truncated: true` + `row_count` 给**真实总数**，模型自己决定要不要继续取
- `sql`：读类走 `run_sql`（模型自己写）时回带一份，便于自查

### 写类返回

三种状态：

| 状态 | 何时 | 给谁 |
|---|---|---|
| **待确认** | 找到目标、等用户点头 | 用户（卡片） |
| **完成** | 确认后真执行了 | 模型 |
| **失败** | 出错 | 模型（同读类） |

```json
// 完成 —— 增 / 删 / 恢复
{ "ok": true, "table": "...", "affected": N,
  "columns": [...], "records": [[...]] }     // 记录是「库里的整行」

// 完成 —— 改
{ "ok": true, "table": "...", "affected": 166,
  "operation": "reject_count += 1",          // 规则型（transform）：说"干了什么"
  "changes": [ {"before": [...], "after": [...]} ] }  // 明细型（update）
```

记录取「库里的整行」（能看到生成的 id、默认值）。

### 待确认数据（给用户看的卡片）

与「成功返回」**同构** —— 它就是要确认的"执行后结果预览"：

```json
{ "type": "delete" | "create" | "update" | "struct" | "import",
  "table": "projects",
  "columns": [...], "records": [[...]],   // 或 changes / ddl
  "affected": 3,
  "danger": false }
```

- 卡片文案：**前端写死一句**（"若确认上述改动正确，请确认"），后端不传文案
- 危险（全表改 / 大批量删）→ `danger: true` → 前端**用醒目样式**单独呈现
- **列名用中文，后端从表定义取**（替掉前端硬编码的 `FIELD_LABELS`，它只认识 projects）

### 合并结论

**合并要看四项**（确认形态 / 输入 / 执行 / 返回），不能只看确认形态：

- **`create` + `batch_create` → 合并**（四项全同，只差"条数"）→ 合为「新增」
- **`update` + `transform` → 不合并**（只有确认形态同；输入是"值 vs 规则"、执行是"直接写 vs LLM 翻译"、返回是"明细 vs 描述"，全不同）

多一个工具，换来参数不模糊，划算。

### 写结果回模型

已挪到**记忆层**（见「③ 没做完什么」）—— 它本质是"跨轮次的记忆"。

# 记忆层

## 一、定位与第一刀

记忆存在的唯一理由：**让 Agent 在一轮一轮之间保持连续。**

**第一刀：把两件事劈开** —— 现在 `session.py` 一肩挑两，正是它又乱又漏的根：

| | 目的 | 特征 |
|---|---|---|
| **记忆** | 给**模型**，保持连续 | 要精炼、要控制大小 |
| **存证** | 给**人**，翻旧账 | 要完整、不怕大 |

## 二、记忆记三格

| 记什么 | 为了 |
|---|---|
| ① **说过什么** | 接得上话 |
| ② **做过什么** | 知道事情办到哪了 |
| ③ **没做完什么** | 用户点头后能接着做 |

## 三、① 说过什么

- **近期保留原文**（保语境）
- **旧的提取要点**，不压成散文 —— 散文的信息不可控（该留的被挤掉、不该留的占地方）
- 方向：从"把对话揉成一团话" → "**从对话里留下事实**"

## 四、② 做过什么

**和「工具返回」的关系**：同一个动作，两个阶段的模型看到的不一样——

| | 谁看 | 看多少 |
|---|---|---|
| 工具返回 | **当轮**的模型 | 全（含数据） |
| 动作记忆 | **后续轮**的模型 | **概要** |

所以动作记忆**不带全量数据**。

**记什么**：`工具名 + 关键参数 + 结果要点`（结构化）。

**结果要点从哪来**（不额外调 LLM）：
- **规则抽取**：结构化的（`row_count` / `path` / `affected`）—— 免费、准
- **模型的回答**：语义的（结论、关键数字）—— **它当轮已经说过了，是免费的总结**

**三个改动**（都在修现状的毛病）：
1. **带上结果** —— 现在只记"调过哪些工具"，结果全丢
2. **不存 `raw`** —— 现在把每次工具返回的 8000 字符截断版塞进会话文件，文件越滚越大
3. **参数不按位置截前 3** —— 现在 `list(args.items())[:3]` 会把 `table_name` 切掉

**保留**：随对话走（近期全、旧的浓缩），但**动作凭据只浓缩、不删除**（删了模型会谎称自己没做过）。

**绑定**：依附在那一轮上（保持因果顺序）。

## 五、③ 没做完什么

**待办（todo）+ 断点续跑。** 要满足三件：

| | 意思 | 现状 |
|---|---|---|
| **存得住** | 活过重启 | ❌ 存内存 |
| **接得上** | 回到"断在哪" | ❌ 只存候选，没存"断在哪个调用" |
| **续得完** | 执行完把结果给模型 | ❌ 执行完直接给用户，模型不知道 |

**先补一个洞**：中断的那一轮**没进历史**（`run_agent` 只在最终回答时 `add_assistant`，而写操作是中断的）。所以续跑时模型回头看是**空白的**。→ 中断轮要留痕。

**续跑从哪接**：把"用户确认 + 执行结果"**伪装成那次工具调用的返回**喂回模型（方向 A）—— 让模型始终站在同一条线上，它知道自己刚才在做什么。

**单个待办**，不是列表（中断了就停，不会攒）。

# 编排层

## 一、定位

业界叫 **Orchestration（编排）**。作用一句话：

> **把"一次 LLM 调用"，变成"一个能多步完成任务的循环"。**

**这是"Agent 之所以是 Agent"的那部分** —— 没有它，模型只是个一问一答的接口。

## 二、职责（九项）

| # | 职责 | 现状 |
|---|---|---|
| 1 | 上下文编排（每轮给模型看什么） | ✅ |
| 2 | 发起 LLM 调用 | ✅ |
| 3 | 解析输出（回答 or 工具调用） | ✅ |
| 4 | 执行工具 + 回填 | ✅ |
| 5 | 循环 | ✅ |
| 6 | 状态管理 | ⚠️ 只有本轮（`tool_log`）；跨轮的丢在 `session` |
| 7 | 异常处理 | ⚠️ LLM 重试有；`dispatch` 无防御；工具错只靠熔断兜 |
| 8 | 终止控制 | ✅ 轮次上限 / 超时 / 熔断 |
| 9 | **与用户交互（中断）** | ❌ 散在三处，未统一 |

## 三、中断统一（本层核心）

**"中断"是一类机制** —— 停下、问用户、等回复。三种原因：

| 原因 | 场景 |
|---|---|
| **澄清** | 意图模糊 |
| **选择** | 方向不唯一 |
| **确认** | 操作要点头 |

**统一流程**：`中断 → 存成 todo（落盘）→ 展示 → 用户回复 → 断点续跑 → 回循环`。

**A1 转正**：澄清现在靠提示词（赌模型记得问），改成给模型一个 **`ask_user` 工具** —— 它一调，就中断。三种中断走同一条路。

## 四、装备着的账（要在这层算清）

这些是"边做边长"留下的，一起清：

- 熔断按 **(工具 + 参数)** 计数，不按工具名（否则误杀"换参数探索"）
- **压缩检查在循环外** —— 单轮巨任务完全绕过它
- **强制结束（超时 / 熔断 / 到上限）不回写历史** → "答了却不记得"
- **两层重试叠影** —— `nl2sql` 内层的自修正 vs 本层的重试
- **`dispatch` 无参数防御** —— 多传/少传/类型错都击穿整轮

# 交互层

## 一、定位

人怎么跟它说话，它怎么回。分三件事：

| 类 | 包含 |
|---|---|
| **说** —— 人怎么表达 | 输入区 · `ask_user` 弹窗 · 确认弹窗 |
| **看** —— 它怎么回 | 对话流（思考 / 工具卡 / 回答 / 产物）· 轨迹 |
| **翻** —— 回头看 | 左栏会话 · 产物列表 · 数据垃圾桶 · 版本历史 · 数据字典页 · 设置 |

## 二、中断的呈现（已定）

**所有「中断」（问 / 选 / 确认）统一用同一套呈现 —— 两种并存的形态：**

| 形态 | 作用 | 特征 |
|---|---|---|
| **底部弹窗** | **当场交互** | 完整内容，要用户回答（`ask_user` 的选项+输入框 / 确认卡片的候选+按钮） |
| **对话内缩略卡** | **事后留痕** | 显示终态（**已授权** / **已终止**），可点开回看当初的详情 |

**为什么：**
- 「要你回应的东西永远在底部」——固定位置，用户不用找
- 对话流**不再被卡片打断**，它变干净了：只记"发生过什么"
- 缩略卡同时解决"历史留痕"——比一条干巴巴的系统消息强，能回看候选/差异

**为什么不用"分场景"（简单留对话内、复杂弹窗）**：那样"确认"会一会儿在这儿一会在那儿，用户不知道该看哪。**一致性 > 省事。**

### 弹窗版式

```
┌────────────────────────────────────────────┐
│              …（对话流在后面）               │
├────────────────────────────────────────────┤ ← 从底部弹出
│        ● ──── ○ ──── ○      ← 顶部：一排问题，点击切换
│   ◈  你想查哪张表？                          ← 图标(罗盘) + 问题
│   ┌──────────────────┐               ← 选项（≤3）
│   │ 项目表            │ 
│   └──────────────────┘
│   ┌──────────────────┐ 
│   │ 打回记录          │ 
│   └──────────────────┘ 
│   ┌──────────────────┐
│   │  其它            │
│   └──────────────────┘
│   ┌──────────────────────────────────┐     ← 自由输入（永远在）
│   │ 或者，直接说……                     │
│   └──────────────────────────────────┘
│          [ 取消 ]   [ 确认 ]   ← 底部
└────────────────────────────────────────────┘
```

- **一个中断 = 一个弹窗**；顶部那排点是**这一次中断里的多个问题**（A 方案），点击切换
- **配色**：全部用项目 CSS 变量（`--glass` / `--edge` / `--acc` / `--danger`），和现有卡片、设置页同一套料
- **确认卡片共用同一容器**：单个确认 = 顶部只有一个点；问题区换成"候选表"；底部换成"取消 / 确认删除"；`danger` 时描边转红
- **图标**：问题前放品牌图标（罗盘），**纯装饰**——要克制（小、低对比），别抢问题本身的焦点

## 三、恢复页（垃圾桶 + 版本历史）

**入口**：主页面左栏新增按钮「**恢复**」→ 独立页面，内有两个 tab 切换。

**为什么放一起**：两者本质是同一件事的两面 —— **都是"回到过去"**（一个捞回删掉的行，一个把表退回某个时间点）。

### 共同形态

- **按表分组**，每组可**收起**（表多不挤；每张表内部列自然一致）
- **都可搜索 / 模糊查询**：
  - 通用：**表名**（最常用）
  - 垃圾桶：行内容 · 时间
  - 版本历史：时间 · **类别**（因何产生）

### 垃圾桶 tab —— 列**被软删的行**

```
▸ 项目表 (projects)       3 条
▸ 打回记录 (reject_logs)   1 条
   └ 点开 → 该表的表格
```

- 展开后 → 该表的表格：**全列展示**（恢复要看清，不能只挑几列），横向可滚
- **废列弱化/隐去**：`is_deleted`（全是 true）、派生的 `is_*` 布尔（`status_raw` 已表达）
- 行尾显示：**删除时间 · 删除人 · 剩余 N 天**（7 天倒计时，给紧迫感）
- 每行操作：**[恢复]**

### 版本历史 tab —— 列**快照**

```
▸ 项目表 (projects)
    今天 15:32  覆盖导入前 · 166 行   [预览] [回滚]
    昨天 09:10  删表前 · 166 行       [预览] [回滚]
```

- **倒序**（最新在前）
- 每条简化显示：**时间 · 类别（因何产生）· 行数**
- **[预览]** → 看完整表（不是回滚，是看）；从预览里再 **[回滚]**
- **回滚前必须先存一份快照**（回滚本身也是破坏性操作，否则回滚错了救不回）

### 保留策略

| 对象 | 保留期 |
|---|---|
| 软删的行 | **7 天** |
| 快照 | **30 天** |

（两个期不同是**有意**的：快照更重，窗口更长。）

- 用户可**手动删除**（不必等自动清理）
- **自动清理可关闭**（关掉后只增不减，由用户自己负责——但仍要提供这个开关）

## 四、数据字典页

**现状**（`SchemaView.js`）设计得不错，**不推翻，是加东西**：

- "结构只读、语义可编辑"—— 和数据层那条"事实从库来、标注是人加的"一致 ✅
- 草稿/原件分开、保存前列出改动、离开前拦截 ✅
- 编辑用 textarea（字段含义是上百字的取值说明，一行 input 装不下）✅

### 要加的

| 加什么 | 属于 | 可编辑 |
|---|---|---|
| **主键** | 结构 | ❌ 只读（库的事实） |
| **唯一约束** | 结构 | ❌ 只读 |
| **关系** | 语义 | ✅ 可编辑 |

### 关系编辑

**入口**：每张表卡片下，独立一块「关系」区（不散在字段行里）—— 关系是"表与表"的事，放表这一级符合直觉。

```
▾ 打回记录表 (reject_logs)
   [字段表…]
   ── 关系 ──────────────────────
     project_name  →  项目表.project_name      [+ 添加]
```

**面板内容**：

```
本端：  打回记录表 · [project_name ▾]
对端：  [项目表 ▾] · [project_name ▾]      ← 先选表，再选列
基数：  [ 1:N ▾ ]                          ← 可选，不填也行
```

**关系是双向的**：一端声明，**两端都显示**。否则用户切到对端表，会发现"它跟谁有关"是空白——明明有关系却是瞎的。（对端可标方向，如"← 来自打回记录表"）

### 「刷新」按钮

现在它是"手工扫库同步"（因为 `schema_meta.json` 和库可能脱节）。

**新设计下语义收窄**：结构和语义都随建表写入库里，不需要刷了。**唯一还需要它的场景**：有人**绕过系统直接用 SQL 建了表** → 字典里冒出个没有的表。所以它保留，但变成"**发现库里冒出来的新表**"。

# 模型层

## 一、定位

**怎么跟模型说一句话** —— 只管"递出去、收回来"，不管"说什么"（那是编排层/工具层）。对应 `llm.py` + `providers.py` + `config_store.py`。

## 二、现状做对的（保留）

- **配置与应用级偏好分开**：`model / base_url / key` 跟配置卡片走；`max_tokens / temperature / reasoning_effort` 是应用级 —— **换个模型不该连带改输出上限**
- **重试只对可重试异常**（超时/连接/限流），业务错误不重试
- **`reasoning_effort` 填了才带**（硬带会 400）
- **空内容检测**（带上 `finish_reason`，能定位原因）

## 三、核心：能力清单（Capabilities）

把"这套配置认什么"**集中到一处**，别处按它办事：

```
capabilities = {
  tool_calling:     true,
  reasoning:        true,
  reasoning_echo:   false,     # 能不能回传 reasoning_content
  reasoning_effort: true,      # 认不认这个参数
  context_window:   128000,    # 窗口多大
}
```

**一处来源，处处遵守：**
- 编排层回传 reasoning 前先问 `reasoning_echo` → **400 的雷拆了**（现在 `agent.py` 是硬塞回去）
- 带 `reasoning_effort` 前先问 → 不再靠"填了才带"勉强躲
- 给 tools 前先问 `tool_calling`

**能力从哪来**：**C 方案** —— `providers` 预设打底（选供应商自动带上），配置卡片可覆盖。**自定义模型时**（没有预设）给一份保守默认，用户在此基础上改。

**附带收获**：`context_window` 正好治**记忆层**的账 —— 压缩阈值不再硬编码 500000，改为"按窗口推导"（如用到 70% 就压），换模型自动适配。

## 四、三层重试，边界划死

| 层 | 重试什么 |
|---|---|
| **模型层** | **只做网络重试**（超时 / 连接 / 限流） |
| **编排层** | 逻辑重试（模型绕圈、工具失败） |
| **SQL 层**（`nl2sql`） | ❌ **删掉**，归编排层 |

## 五、待定

- **配置切换的时机**：设置页改了配置 → `LLM` 实例要重建（它构造时读死了 active）。谁负责刷新，要明确。

# 横切层

## 一、安全

**收成一个「执行前闸门」** —— 所有 SQL 出门前都过它，不管从哪来（模型写的 / 服务拼的 / DDL）。

```
生成 SQL / 模型写 / 服务拼  → 【执行前闸门】 → 数据库
                              检查三件：
                              ① 标识符白名单（表名/列名是不是表定义里真有的）
                              ② 语句类型对意图（read→只 SELECT；write→只 DML；ddl→结构）
                              ③ 系统字段 / 全表检测
```

- **位置**：**执行前**，不是"生成后"（现在的 `guard` 卡在 `nl2sql` 里，只罩得住那条路）
- **放行判据**：执行时带意图 `purpose="read" | "write" | "ddl"`
- **不合规怎么办**：**拦下来 + 返回错误**（`{ok:false, error_type:"security"}`），**不抛异常** —— 让模型看得懂、能换条路，整轮不被击穿

**这补上两个缺口**：写路径/DDL 也被罩住；白名单校验有了家。

## 二、可观测

**audit 和 trace 性质不同，去处不同：**

| | 是什么 | 去哪 |
|---|---|---|
| **audit** | **业务凭据**（谁、何时、改了什么） | **进数据库**（一张内部表） |
| **trace** | **观测日志**（这次跑得怎么样） | **留文件** |

- **audit 进库**：这样"改库 + 记审计"**在同一个事务里** → 原子。现在它是追加文件，**不原子**（改成功审计失败=没账；审计写了库没改=假账）
- **trace 记什么**：问题 · 走过的工具 · **中断过几次**（新机制）· 耗时 · token · 错误

## 三、配置

框架（`settings_spec` 单一真源、分级、risk 说明）**很好，保留**；但**参数要重过**（设计变了）。

### 参数的增删改

| 参数 | 处置 |
|---|---|
| `llm.base_url` · `llm.model` | **删** —— 僵尸（代码早不读，走配置卡片） |
| `env.DEEPSEEK_API_KEY` | **删** —— 与配置卡片的 key 重复，收敛到 `secrets.json` |
| `agent.tool_result_limit` | **重新定位** —— 明确成"工具返回在**界面**上的展示上限" |
| `display.max_llm_rows` | **改名** → "读类返回给模型的行数上限" |
| `agent.compact_threshold` | **改成「触发比例」** —— 阈值 = 卡片 `context_window` × 比例 |
| **快照保留期** · **快照自动清理开关** | **新增** |

### 设置页的分层原则

**设置页 = 用户偏好，不是 Agent 内部参数。**

| | 是什么 | 怎么办 |
|---|---|---|
| **用户偏好** | "我想要什么"（选择） | **留在设置页** |
| **内部参数** | "系统怎么跑"（工程决策） | **搬进「开发者模式」**（默认关、入口低调） |

**留下（用户偏好）**：模型（配置卡片）· 生成随机性 · 思考强度 · 输出上限 · 批量确认阈值 · 全量展示阈值 · 抽样条数 · 导入冲突抽样 · 预览行数 · 软删保留期 · 快照保留期 · 快照自动清理开关
