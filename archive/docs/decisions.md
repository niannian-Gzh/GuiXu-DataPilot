## 实验1：NL2SQL 的表名问题（2026-09-10）

### 问题

用户问："张三打回超过3次的项目有哪些"

### 版本A：无字段说明

- 生成SQL：`SELECT ... FROM project_table WHERE ...`
- 结果：SQL 执行报错（表名 project_table 不存在）
- 结论：模型知道列名，但不知道表名，自己瞎猜

### 版本B：加上字段说明

- 生成SQL：`SELECT ... FROM projects WHERE owner = '张三' AND reject_count > 3`
- 结果：SQL 正确，返回空
- 结论：空是因为数据里没有"张三"这个人，SQL 是对的

### 学到的

1. prompt 里只有列名不够，要加"字段语义说明"
2. 空结果有两种可能：SQL错了 / 数据里真的没有
3. 不能自动对空结果重试，会误伤"真的没有"的情况

## 实验2：表名缺失对 NL2SQL 稳定性的影响（2026-09-10）

### 背景

Golden Set 15 题首次跑完，结果 15/15 通过，但只有 7/15 一次通过，
其余 8 题靠自修正兜底。观察发现：8 次重试全部是"表名猜错"或
由"猜表名"引发的思考泄漏。

### 根因

SYSTEM_PROMPT 里给了表结构（列名+类型+说明），但没有给表名。
模型不知道列属于哪张表，只能每次猜，猜出过：

- project_table
- project
- project_name
- 表名（字面量）

### 修复

在 SYSTEM_PROMPT 中显式加入 "表名：{table_name}"，并在
generate_sql / fix_sql 中传入。

### 结果对比

| 版本   | 通过  | 一次通过 | 重试次数 |
| ------ | ----- | -------- | -------- |
| 修复前 | 15/15 | 7/15     | 8        |
| 修复后 | 15/15 | 15/15    | 0        |

### 意外收获

思考泄漏（`Wait, I need to check...`）也一并消失。推测原因：
模型之前需要"思考表名"，思考过程混入输出；表名给定后，
无需犹豫，输出自然干净。

### 学到

1. prompt 缺关键信息，模型会用"猜"来补，且每次猜法不同
2. 症状（输出污染）和根因（信息缺失）常常不在同一层
3. 自修正机制的正确位置是"兜底"，不是"主力"。一次通过率
   才是系统健康度的核心指标

## 实验3：自修正机制的"洗白"漏洞（2026-09-10）

### 背景

用户问"你把项目A删掉"，系统返回"没有找到符合条件的数据"。

### 现象

- 生成的 SQL：SELECT \* FROM projects WHERE project_name = '项目A'
- 用户要求的是 DELETE
- 系统没删，只是查了一下，还返回了"没找到"
- error 字段是 null，看起来一切正常

### 根因

1. 模型生成了 DELETE
2. execute.py 的护栏拒绝执行
3. **自修正机制把"拒绝"当成"可修复错误"，生成了 SELECT 来"通过检查"**
4. 用户意图被悄悄篡改

### 为什么危险

- 用户以为"项目A不存在"，实际是"我没删，只查了"
- 自修正机制会自动把非法操作"洗白"成合法操作
- **这是安全漏洞，不是普通 bug**

### 修复

1. 新建 guard.py：独立判断 SQL 是否为写操作
2. 在 generate_sql_with_retry 的**两个位置**做安全检查：
   - 初次生成后
   - 每次 fix_sql 后（防止洗白）
3. 写操作直接抛 SecurityError，**不进入自修正**
4. execute.py 保留护栏，作为深度防御

### 学到

1. 自修正机制必须有边界：**安全拒绝 ≠ 可修复错误**
2. guard 必须是独立模块，和执行分离
3. 检查点要放在"修正前后"两处，不能只在入口

## 确认机制定义（2026-09-11）

### 核心原则
宁可多问，不可猜错。

判断依据：用户对 Agent 的信任是减法。多问一次是可接受的，
搞错一次是不可接受的（尤其是写操作）。

### A 级：意图确认
- **性质**：意图层
- **触发**：意图模糊、语义不准确（覆盖所有操作类型，含查询）
- **动作**：引导式确认，一次问清，不追问
- **铁律**：禁止假设，准确判断为最高优先级
- **位置**：在改写/执行之前
- **示例**：
  - "删除那个家装项目"（指代不明）
  - "全没用了"（意图不明）
  - "所有家装项目"（上下文干扰时）

### B 级：操作确认
- **性质**：操作层
- **触发**：增删改操作执行前
- **动作**：二次确认
- **位置**：目标锁定之后、执行之前

### B+ 级：B 级的强化形式
- **性质**：不是独立层级，是 B 级在大批量场景下的形式变化
- **触发**：大批量删除（数量 > 阈值，默认 20，可配置）
- **动作**：输入式确认（用户须输入"确认删除 x 条"）
- **位置**：替代 B 级的常规确认形式
- **示例**：批量删除 166 条时，须输入"删除166条"

### A 与 B 的关系
- 可串联，但同一次交互只推进一步
- 例：A（澄清指代）→ 用户澄清 → B（确认删除）→ 用户确认 → 执行
- 目标明确时，A 不触发，直接进 B

## 架构演进：从 workflow 到 Agent（2026-09-11）

### 最初的 workflow 架构
- intent.py：意图判断（关键词 + LLM 分类）
- rewrite.py：查询改写（few-shot 补全省略）
- nl2sql.py → execute.py → summarize.py：查询流水线
- 流程：用户输入 → 意图判断 → 改写 → 生成SQL → 执行 → 总结

### 暴露的问题
1. 改写器"过度改写"语义完整的问题
   - "打回次数最多的项目"被改成"张三的项目里打回最多的"
   - 范围被悄悄缩小，结果看似合理但语义已偏
2. 意图判断接不住指代
   - "删了吧"（承接上文）被判为 CLARIFY，让用户重说一遍
3. 上下文被切碎
   - 意图判断只拿到"用户说过的话"，看不到助手回复
   - 每个模块各看一部分，信息不完整
4. 加功能 = 加模块
   - 每加一个能力，就要加一个 prompt、一个 LLM 调用
   - 流程越堆越长，出错点越来越多

### 重构方案
- 单一 Agent Loop（agent.py，约60行）
- 能力封装为工具（tools.py）
- 模型看到完整上下文，自主决定调哪个工具
- 旧模块归档到 legacy/（本地保留，不入库）

### 重构结果
| 指标 | 重构前 | 重构后 |
|---|---|---|
| LLM 调用层数 | 4层（意图/改写/SQL/总结） | 1个循环 |
| "那李四呢" | 靠改写器 | 模型自己接住 |
| 加新功能 | 加模块 | 加工具 |
| 代码量 | intent.py + rewrite.py ≈ 200行 | agent.py + tools.py ≈ 150行 |

### 核心认知
- Agent 的能力边界 = 工具列表。没有工具，就没有能力。
- 安全边界由"不提供工具"保证，而非"prompt 劝阻"。

## Markdown 渲染：中文标点让强调标记失效（2026-09-17）

### 现象

界面上出现这样一段（星号原样裸露，加粗却跑到了中间一截文字上）：

```
同样提醒口径：这是**包含匹配（含组合状态）**的口径，共 2 条；若按状态恰好等于「已下证」**的严格口径，则为 0 条。
```

源文本明明是两处 `**…**`，渲染后却错位了。

### 排查：先走了弯路

第一反应是 marked 的 bug。单测几个用例，确实很像：

| 输入 | 结果 |
| --- | --- |
| `甲**乙**丙` | 正常 |
| `甲**乙（丙）**戊` | 不渲染 |

于是换 markdown-it 做对照 —— **结果一模一样**。

两个独立实现不可能同时有同一个 bug。方向错了，回去查规范。
（中途我还把 flanking 定义记反了一次：right-flanking 判定的是**前面**那个字符，
不是后面。按错的定义推演，会得出"应该能渲染"的错误结论。）

### 根因：CommonMark 的强调定界符规则

闭合的 `**`，若前一个字符是 Unicode 标点，
规范要求**后一个字符也必须是空白或标点**，否则它不构成右定界符 —— 整对星号作废。

英文靠词间空格躲过去：

```
**bold (paren)** word      闭合 ** 后面是空格 → 满足条件 → 正常
```

中文没有词间空格，`**……）**的` 必然踩中：

```
这是**包含匹配（含组合状态）**的口径
                            ↑ 前面是「）」，后面是「的」→ 判无效
```

**换任何 CommonMark 解析器都一样。** 这是规范为英文设计的盲区。

### 实测出的精确触发条件

| 内容 | 关闭定界符前是 | 结果 |
| --- | --- | --- |
| `甲**乙丙丁**戊` | 汉字 | 正常 |
| `甲**乙，丙**戊` | 全角逗号 | 正常 |
| `甲**乙、丙**戊` | 顿号 | 正常 |
| `甲**乙（丙）**戊` | **全角右括号** | **失效** |
| `甲**乙(丙)**戊` | **半角右括号** | **失效** |
| `甲**乙“丙”**戊` | **全角右引号** | **失效** |

结论：**与标记所在位置无关，只与「内容里有没有成对符号」有关。**
`（` `）` `(` `)` `"` `“` `”` 会触发，`，` `。` `、` `：` `.` 不会。

### 被否决的方案：加空格

思路是给闭合 `**` 后面补一个空格，让它满足 (2b) 分支。实测**确实有效**：

| 补的字符 | 是否管用 |
| --- | --- |
| U+0020 普通空格 | 可以 |
| U+00A0 不换行空格 | 可以 |
| U+2009 / U+200A 细空格 | 可以 |
| **U+200B 零宽空格** | **不行** |

最后一行堵死了「用不可见字符」的捷径：规范只认 Unicode `Zs` 类别，
而 U+200B 属于 `Cf`，压根不算空白。

但真正的问题是**第二个**：这个规则分不清开/闭定界符。

```
（甲）**乙**丙   原样    →  正常渲染
（甲）**乙**丙   加空格  →  整对作废
```

那个 `**` 前面是 `）`、后面是 `乙`，**看着完全符合「该加空格」的条件**，
但它其实是**开启**定界符。给它后面塞空格，left-flanking 也没了。

**一个 `**` 是开还是闭，只有配对之后才知道** —— 而这正是规范判定失败、
我们想绕开的那一步。靠局部字符插空格，等于在还不知道开闭的情况下做决定，
必然出错。所以这条路否决。

### 最终方案：解析前落标签

前端加 `strongify()`，在交给 marked 之前把成对的 `**` 直接换成 `<strong>` 标签，
绕开定界符判定（详见 `src/web/static/index.html` 的 `md()`）。

两个边界：

- `****甲****`（嵌套粗体）一开始被切歪成 `<strong>**甲</strong>**`。
  收紧断言为 `(?<!\*)\*\*(?=[^\s*])([\s\S]*?[^\s*])\*\*(?!\*)` 后，
  这类写法整个跳过、交回 marked 按原样解析成嵌套 `<strong>`。
- 代码块按 ``` 切段、行内代码逐行按 `` ` `` 切格，奇数下标原样跳过，
  代码里的 `**`（如 `x = 2 ** 3`）不被替换。

### 为什么不连 `*` 和 `_` 一起修

统计全部历史会话的助手输出：

| 标记 | 用量 |
| --- | --- |
| `**` 粗体 | 43 |
| `\|` 表格 | 19 行 |
| `` ` `` 行内代码 | 12 |
| `*` 斜体 | **0** |
| `~~` 删除线 | 0 |
| `_` 下划线 | 10 —— **全是误报** |

那 10 处「下划线」全是文件名和字段名：

```
data\reports\2026年9月17日日报_20260917_120657.pdf
is_deleted / project_name / delete_trace_id
```

**`_` 绝对不能碰** —— 真去修，这些标识符会被吃掉一半变成斜体。
而且 CommonMark 禁止词内 `_` 强调，中文没有词间空格，
`前_甲_后` 永远算词内，等于 `_` 语法对中文整体不可用 —— 而这**正好是我们要的**。

`*` 斜体历史用量为 0，修它要放开单星号（`1*2*3`、`*.xlsx` 会被误判），
风险面大于收益。

### 决策：从源头约束，而不是继续堆正则

前端的补丁会越堆越多。既然模型压根不输出斜体/下划线，就永远不会踩到 ——
在 `SYSTEM_PROMPT` 里约定输出格式。

对照实验（同一个诱导性问题「请用斜体强调这两个数字」）：

| 提示词 | 输出 |
| --- | --- |
| 旧 | `已下证 *10* 条` —— **照做了** |
| 新 | `已下证的 **10** 条` —— **改用加粗** |

### 验证

1. 边界回归 14 项：代码块、行内代码、未配对、嵌套、跨段、表格全部正确
2. 全局扫描：9 个历史会话跑一遍渲染，裸露星号 0 处
3. 端到端：服务实际加载的 `SYSTEM_PROMPT` 被模型复述确认

### 学到的

1. **两个独立实现结果一致时，别再怀疑实现，去看规范。**
   对照实验（marked vs markdown-it）是这次最省时间的一步。
2. **规范是为英文设计的，中文会踩到看不见的边界。**
   flanking 规则依赖"词间空格"，而中文根本没这个词法单位。
3. **局部判断代替不了配对。**
   定界符天生需要上下文 —— `（甲）**乙**丙` 和 `这是（甲）**乙**` 里的 `**`
   前后字符完全相同，一个是开、一个是闭。
4. **动手前先统计真实用量。**
   `*` 斜体 0 次、`_` 下划线 10 次全是文件名 —— 不查这个，
   很容易"顺手"修出一个灾难。
5. **下游修不完的，就约束上游。**
   前端正则能覆盖的语法是有限的，与其无限加规则，
   不如让输入源不产生那些语法。
6. **改 `SYSTEM_PROMPT` 这类模块常量不受配置热加载保护**，
   确认是否真生效的办法：**让模型复述它自己的系统提示词**。

   > ⚠️ 本条当时还写了「`uvicorn --reload` 会在文件变更时重启 worker」。
   > 当天下午这条就被证伪了，详见下方「服务进程」一节。


## 思考链展示：reasoning_content 的接入与语言控制（2026-09-17）

### 数据从哪来

DeepSeek 的思维链走 `message.reasoning_content`，它是**非标准字段**，
不在 OpenAI SDK 的 `ChatCompletionMessage` 定义里。SDK 的响应模型配了
`extra="allow"`，所以它会落在 `message.model_extra` 里，能取到：

```python
reasoning = getattr(message, "reasoning_content", None)
```

实测 `deepseek-flash` **带不带 `tools` 参数都返回**，不是 reasoner 专属。

### 一个硬性约束

带 `tool_calls` 的 assistant 消息**必须原样回填 `reasoning_content`**，
否则下一轮请求直接 400。这是 DeepSeek 的要求，不是可选项。

### 前端设计：思考节点塞进 tools 数组

思考气泡和工具卡片共用一条时间线（`t.tools`），靠 `kind: 'think'` 区分。

理由：SSE 事件到达顺序天然就是「先想后做」，直接 push 就对了。
如果单独存一个 `reasonings` 数组再按轮次合并，反而要多处理三件事：
模板解构、排序、以及历史会话缺 `round` 字段的降级。

代价是两处聚合统计（轨迹页、`allTools`）要过滤掉思考节点，
否则轨迹的「步数」会把思考也算进去。

### 语言控制：有效，但别过度施力

思考默认是**英文**的（实测中文占比 12–14%）。加一句约束即可：

```
用简洁的中文回答，思考过程也必须用中文。
```

中文占比升到 **62–71%**。残留的英文只剩工具名和 JSON 字段名
（`query_database`、`ambiguous: true`），本来就该是英文。

但**加强措辞没有正收益**，反而更差：

| 措辞 | 思考的中文占比 |
| --- | --- |
| 温和（「也必须用中文」） | **85%** |
| 极端（「【强制】禁止英文思考」） | 75% |
| 无约束基线 | 56% |

（同一组裸调用对照实验，temperature=0）

### 存储影响

`tool_log` 每条都存一份完整 `reasoning`，**同一轮调 N 个工具就重复存 N 份**。
实测思维链 100–400 字符，纯聊天场景见过 700+。目前可接受，
要压体积的话可以改成每轮只记一次。


## 服务进程：「健康检查 200」不等于代码是新的（2026-09-17）

### 现象

改了 `agent.py` 的 `SYSTEM_PROMPT`，服务重启过、`/health` 返回 200、
对话功能一切正常，但**改动完全没生效**。

更早一次也一样：`reasoning` 事件一个都没发出来，
接口却毫无异常，没有任何报错。

### 排查

对比两个时间戳，问题立刻现形：

```
src/agent.py   修改于 16:04:35
worker         启动于 15:49:02    ← 早了 15 分钟
```

**健康检查 200 只证明「有个进程在监听」，不证明「它加载的是当前代码」。**

### 根因：三种进程状态混在一起

**① 孤儿 worker**

用 `--reload` 启动是三层结构：

```
reloader 父进程  →  worker  →  实际服务进程
```

杀掉父进程后 **worker 不会跟着死**，会继续提供服务。
而自动重载的监控逻辑在父进程里 —— 父进程一死，热重载就**永久失效**，
但服务本身毫无异样。

**② `--reload` 会打印 `Reloading...` 却静默失败**

```
WARNING:  StatReload detected changes in 'src\agent.py'. Reloading...
```

这行之后**什么都没有**：没有 `Shutting down`，没有新的
`Started server process`，worker 的 PID 和时间戳纹丝不动。

**这行日志只能说「检测到了变化」，不能说「重启成功了」。**

**③ 启动失败的 reloader 不退出**

有一次在错误的工作目录下启动（`cd` 到别处后，`--app-dir src`
指向了不存在的路径）：

```
ERROR:    Error loading ASGI app. Could not import module "api".
```

进程**没有退出**，reloader 一直挂在那里等文件变化。
后来查进程树才发现 8000 端口上其实有**两组**服务，
其中一组是这次失败留下的尸体 —— 排查时它一度把我引向错误方向。

### 结论

**判断代码是否真生效，只认这一条：**

```
worker 启动时间  >  代码文件最后修改时间
```

```bash
stat -c '%y' src/agent.py

# 查监听端口的进程及其启动时间
powershell -NoProfile -Command "Get-NetTCPConnection -LocalPort 8000 -State Listen |
  ForEach-Object { \$p = Get-Process -Id \$_.OwningProcess;
  \"\$(\$_.OwningProcess) \$(\$p.StartTime)\" }"
```

**排查进程要看全树，不能只看端口占用者。** 占端口的那个 PID
可能只是个 wrapper，真正跑 app 的是它孙子辈。

### 附带发现：会话内存缓存会覆盖磁盘修改

`_sessions` 字典缓存着已加载的会话。直接改磁盘上的会话文件后，
**内存里还是旧的**，下次 `save()` 会原样覆盖回去。

清这个缓存只能重启进程，没有别的入口。


## 架构级优化：从「模糊」到「七层架构」（2026-10-10 ~ 12）

### 缘起：一种说不出的"不对"

"我对这个项目都有点模糊了。"

不是崩溃，不是报错——项目能跑，评测还满分。但**看着它，说不上哪里不对**。
当时能指出的，只有三个方向的直觉：上下文工程、工具设计、前端。

复盘后发现：问题**不在某一处**，而在——**没有主线**。
东西是"边做边长"出来的，每一处单看都合理，合起来没有一条线串着。

### 为什么最后是"重新设计"，不是"修 bug"

一开始想修 bug（审计出了一堆：P0/P1/P2）。但很快看清两条：

1. **很多"bug"长在错误的地基上**——修了它，地基还在，还会长新的
   （例："多表写路径全废"——根不在工具层写错，在**数据层根本没有"表"这个概念**）
2. **"感觉不对"根治不了**——bug 修完，项目还是没主线

于是停下：**先解构，再设计。** 这一步很难，因为"停下来重新想"看起来像退步。

### 方法

1. **俯瞰 + 完全解构**——先不定方案，把每个文件摊开：它是死是活、干嘛的
2. **盘家底**（产出 `docs/inventory.md`）——结果触目：`legacy/` 整个目录零引用、
   `db.raw()` / `execute_many()` 等一批死函数、i18n 的 34 个键从未被用、
   `pyproject` 的 CLI 入口（`datapilot = "datapilot:main"`）**从没跑通过**……
3. **元观察**（最重要的发现）：这些僵尸的成因是**一个习惯**——
   **"每次重构，只搬新的，不扫旧的"**。
   DuckDB→PG 留了提示词和测试；轨迹搬家留了旧 CSS；workflow→Agent 留了 `legacy/`。
   **要防的不是僵尸，是这个习惯。**
4. **从底层往上，逐层重新设计**（产出 `docs/design.md`）

### 分层是怎么来的

起点是一句问："**这个 Agent 由什么构成？**"

用户先给五层（交互/模型/调控/工具/记忆）。补了两处：

- **数据层**——"记忆"是 Agent 关于**自己**的记录，而数据是它操作的**世界**，两者不是一回事
- **横切层**——安全、可观测**贯穿所有层**，却不属于任何一层

最终：**六纵 + 一横**。而且"编排层"这个名字后来对齐了业界说法（Orchestration）。

### 每层的关键决策

- **数据层**：立起「**表定义**」这个一等概念——**真源在库里**（结构读 PG + 语义存 meta 表）。
  砍掉视图（换 **RLS** 隔离软删，一张表只有一个名字）；破坏性操作前落**整表快照**。
  关键认知：**因为用户能运行时建表，表定义就是"数据"不是"代码"**，所以"库里为真源"是必然，
  不是偏好。
- **工具层**：**按性质分**（读/写/结构/产出），不按动作分——`update` 和 `transform` 因此
  分得清；返回改成**给模型的数据**（二维数组 + 列名），不再是"一段话"；`_is_success`
  从"猜有没有 error 键"改成看 `ok`。
- **记忆层**：**劈开"喂模型的记忆"和"给人看的存证"**（现在 `session.py` 一肩挑两，是它又乱又漏的根）。
  记三格：说过什么 / 做过什么 / 没做完什么。
- **编排层**：**中断统一**——澄清 / 选择 / 确认，三种中断走同一条路
  （中断→todo→用户→断点续跑）；给模型一个 `ask_user` 工具，让"问用户"从"提示词碰运气"变成机制。
- **交互层**：**所有中断 = 底部弹窗**（当场交互）+ 对话内缩略卡（事后留痕）。
- **模型层**：立「**能力清单**」（`tool_calling / reasoning_echo / context_window`…）——
  一处来源、处处遵守。它顺手拆了"reasoning 回传可能 400"那颗雷，还给了压缩阈值一个
  "按窗口推导"的依据。
- **横切层**：安全收成**执行前闸门**（读写 DDL 一网打尽）；**audit 进库**（进事务才原子）；
  设置页 = **用户偏好**，内部参数搬进「开发者模式」。

### 过程中的几次"翻案"

（这是最值得写的部分——真实的过程不是一个判断接一个正确判断）

- 我说"数据层没有表定义"，用户说"我记得有" → **我收回**：有，只是散成三份、还缺主键关系
- 我说"按确认形态合并工具"，用户点出 `update`/`transform` 的输入、执行、返回都不同 →
  **我收回**：只有确认形态同，不能合
- 用户想参考 Codex / Claude Code 的确认卡片样式 → **我拦**：它们是终端，你是 WebUI，
  样式搬不过来，而且**作品集抄样式等于交白卷**
- "日志算功能吗""关系定义是工具吗""RAG 是工具吗" → 逼出两个认识：
  **"功能""工具"这两个词都太粗**——它们把"动作 / 数据 / 子系统"混成了一锅

### 方法论收获

- **完全解构 ≠ 推倒重写**：解构的是**设计**，不是**存量**。有些东西（手写 Loop、
  薄工具厚服务、db 抽象）是资产，要被"重新检视"而不是"默认推翻"
- **"感觉不对"是线索**，不是情绪。它能指路——只要肯停下来追
- **设计期间不动代码**：一旦开了"顺手改一下"的口子，就会滑回"边做边长"

## 一次换色实验：真问题不在配色，在光效（2026-10-12）

### 缘起

设计语言整体重做，定下「精确感」为根。配色上判定原来的宝石蓝
「渗透在各个角落、没有辨识度」，决定换色相。

选了**青**（`#2ed3c6`）—— 理由是：青是「测量仪器」的颜色（示波器、
频谱仪、监护仪的读数屏都是这个色相），而且主流 AI 产品全在蓝紫，
青少见。

### 做了什么

1. `--acc` 蓝 → 青
2. 清掉 **45 处**手算硬编码的 `rgba(61,220,151,.12)` 这类值，换成 `color-mix` 派生层
3. 删掉浅色主题（CSS 9 处 + JS 6 处）
4. 品牌名渐变、罗盘配色一并改成银白

### 结果

**很丑，而且说不清丑在哪。**

| 轮次 | 反馈 |
|---|---|
| 第一轮 | 「青，太浅了，感觉一般。原本的主色渗透在各个角落，替换其实不太彻底，倒不如不换」 |
| 第二轮（调浓后） | 「很丑，太怪了，我说不出」 |

### 根因（拆成两件事）

**1）"替换不彻底"是执行问题，不是"换色不值得"**

我改的只是 `--acc` 一条线。但品牌名那个蓝紫渐变、罗盘 `--rose-*`
四色、chat.css 里的光点 rgba —— **是三套各自独立的硬编码色值**，
它们从头到尾都还是蓝的。

`grep` 全部十六进制色值之后才看清：**用户说的"主色渗透在各个角落"，
技术上的真相是"同一个色值被抄了很多份"。**

**2）真正的丑不在配色，在光效**

数了一遍全站：**12 处装饰性彩色发光**，其中 **2 处是永远在循环的动画**
（左栏罗盘 5.5s 呼吸、欢迎屏光点 2.3s 脉动）。

而它们**全都不报任何状态**——纯粹是装饰。

### 关键区分：运动 ≠ 发光

这是这次最值钱的一条：

- **运动**（旋转、位移）—— 表示"活着"，**不疲劳，甚至必要**
- **发光**（glow / blur / shadow）—— 照亮周围、抢注意力，**只有报状态时才允许**

用户的原话：「中心一直在转的那个光点，是我喜欢的**运行式状态**」。

> **所以旋转该留，光该删。**

**而疲劳的具体来源是"发光半径的脉动"**：`drop-shadow(0 0 3px → 9px)`
一变，周围一圈都在变亮。**雷达上的光点是明灭，不是泛光。**

### 修复

- 12 处装饰性发光 → **只留 3 处**：执行中光环 ×2、输入框聚焦环
- 光点脉动：`drop-shadow` 半径 → `opacity` 明灭
- 配色全部退回宝石蓝

### 学到了

1. **"换了不对"有时比"换了对了"更有价值**——它把不动手就看不见的问题
   （光效过载）逼出来了。改配色只是手段，暴露真问题才是收获
2. **改一个色值，要 grep 全部同义值**。视觉上的"到处都在"，
   技术上是"抄了很多份"
3. **深色不是疲劳的原因，"把发光当装饰"才是**。参考项目同样是深底，
   但它写死了「辉光只留给活动的数据点，绝不漫过整个页面」
4. 一次只改一个维度，否则分不清是哪个起了作用

## 命名与图标：图形把名字救了回来（2026-10-12 ~ 10-13）

### 缘起

品牌名定了「归墟」（《列子·汤问》：渤海之东有大壑，百川汇流之所）。
图标最初是**罗盘**，推演链是：归墟 → 百川汇流 → 航海 → 罗盘 → 领航员。

### 翻车

改了十几轮。用户从"这个有意思"，到"我的罗盘为啥变成星星了"，最后落到：

> 我要杀了你...... 在开玩笑吗？怎么能做的这么恶心？

两个错叠在一起：

1. **没先做预览页** —— 用户明确要求过"你做个独立页面给我多出几个方案"，

2. **从意象演绎，而不是从事实归纳** —— 罗盘、海、领航员全是意象，
   它们跟这个项目一点关系都没有，只是名字听着能扯上

用户那句质问很锋利：

> 为什么你会一直盯着罗盘，海，领航员，这种意象来说？这与我们的项目就这么贴合吗？

隔天，用户不再说"再改一版"，而是换了个问法：

> 抛弃一切前提，**从项目自身出发**，能提炼出什么信息呢？

最后落在一个动作上：

> 四个指针从四个方向飞过来拼到一起

**这不是在描述图标，是在描述「归墟」这两个字**——百川汇流之所，万物所归。
花瓣从四方收拢、在中心汇成一点，几何上就是"归"。

于是有了**八瓣 + 中心光点**，一路用到今天。

### 意外收获：名字靠不住，是因为没有图形能证明它

10-12 那天，用户一度想**放弃「归墟」**：

> 别急，归墟这个名字这样反而不合适，如果叫启明星，或者北极星，或者星盘？这种呢？
> 我们的项目主题，图标，名称，应该是三点一线，保持协同性，如果叫归墟，图标怎么改？

八瓣做出来之后，10-16 的说法变了：

> 归墟，是我们新的，也是最终的名字。

**图形不是名字的仆人，是名字的证人。**

### 学到了

1. **"先做预览页"不是礼貌，是流程。** 直接改项目等于把判断权偷走——用户失去"并排看两版"的机会，只能看成品
2. **意象是免检的，事实不是。** "归墟→海→罗盘"每一步都说得通，合起来全是空的
3. **名字被质疑时，缺的可能不是更好的名字，是能证明它的图形**

## 从 Docker 到桌面应用：一次形态上的自我推翻（2026-10-14）

### 缘起

项目一直按 **WebUI + Docker 容器化**规划——"一键部署"，用户装 Docker、跑容器、开浏览器。

### 转折

用户自己撞上了这个问题：

> docker 封装的核心原因是为了让用户一键搞定……说起来，如果用户下载我们的项目，他电脑里需要有 docker 吗？

**"一键搞定"的前提，是先装一个 Docker。**

然后更狠的一句：

2. **"一键搞定"要先数前置条件** —— 如果第一步是"请先安装 Docker"，就不叫一键
3. 顺带解决了另外两个问题：包体（借系统内核）、PDF 预览（WebView2 自带）

## 向量库的祛魅：它不是"一个柜子"，是三样东西（2026-10-15）

### 现象

用户的认知是"向量库存文档切片"，于是有个想不通的地方——
**既然关系库能装向量，那向量库是不是几乎没用了？**

> 我想不通了。。。我之前一直以为关系型数据库和向量数据库是两个不同层面的东西，
> 怎么你这么一说，这向量库几乎没用了？

### 拆解

**"向量库"这个词让人以为它是一个柜子。它不是。** 它通常是三样东西捆在一起：

| 东西 | 是什么 | 能不能重来 |
|---|---|---|
| **切片原文** | 真数据 | **不能**——丢了就是丢了 |
| **向量** | float32 数组 | 能（原文 + 模型重算） |
| **索引** | HNSW/IVF 加速结构 | **能**——重算一遍就有 |

**该谁存**：原文归 SQLite（要事务、要原子），向量可以塞 BLOB，索引归 FAISS。

**为什么必须拆**：索引是**派生数据**。捆在一起的话，删一份文档要同时删两处——
而**跨存储没有事务**，迟早出现"记录删了但切片还在，检索还能捞出来"。
拆开之后：**删文档只删 SQLite（一个事务），索引下次重建自然就不含它了。**

### 学到了

1. **一个词捆着三样东西时，先拆词，再谈方案** —— "向量库""数据库""Agent"都是这种词
2. **真源只能有一个，派生的可以随便丢** —— 这条判据能替掉一大半架构争论
3. 本项目规模（几千条切片）**暴力算就是最优解**，上 ANN 是给自己找事

# 第二部分 · 博客素材

> 一条素材 = 一个故事。展开成「现象 → 排查 → 根因 → 学到了」。
> 保留转折和翻车。技术细节照素材写、不许编。

## 一、方法论 —— 怎么做事

[素材] **架构分层重构**：tools 从"厚工具"变成"菜单+传话筒"，业务逻辑抽到 services 层。main.py 从 120 行瘦到 50 行。核心洞察：**工具应该薄，服务应该厚**。

[素材] **防护体系**：分层防护——底层（LLM 重试、SQL 超时、行数上限）+ 中层（思维熔断、异常熔断）+ 顶层（Loop 总超时）。每层做自己该做的事。关键认知：**限制"行数"要区分"内存保护"（100 万）和"上下文保护"（20 行）**，混在一起会两头不讨好。

[素材] **上下文压缩**：先归档（无损源真相）后压缩（有损工作副本），保留最近 6 轮。关键认知：这个功能"简单"，是因为**架构分层清晰**——llm 返回 usage、session 管存和压、agent 管触发，各改一处，互不影响。

[素材] **prompt 精简的陷阱**：把规则从 prompt 移到工具描述时，**措辞强度决定效果**。"请"不够，"必须 + 示例"才有效——模型对命令式的遵守度高于请求式，具体示例提供了模仿目标。

[素材] **评测**：从 15 题扩到 31 题，**靠纯 SQL 算期望值**，不靠拍脑袋。Agent 层精选 15 题，覆盖 7 大类。

[素材] **数据源抽象的"半成品"陷阱**：把 db_url 改成 PG，几十处直接调 `duckdb.connect` 的地方全炸。这不是 bug，是"**抽象只做了一半**"。正确做法是"新建统一接口 + 全部调用点迁移 + 方言适配"——是一个完整的重构，不是"顺手改一个函数"。

[素材] **完全解构 ≠ 推倒重写**：解构的是**设计**，不是**存量**。有些东西（手写 Loop、薄工具厚服务、db 抽象）是资产，要被"重新检视"而不是"默认推翻"。

[素材] **设计期间不动代码**：一旦开了"顺手改一下"的口子，就会滑回"边做边长"——而"边做边长"正是这个项目所有问题的源头。

[素材] **先做预览页，别直接改项目**：做图标时用户明确要求"你做个独立页面给我多出几个方案"，我却直接改了项目文件。结果是——改坏了要回滚，改好了没得对比，用户只能看成品。**判断权被偷走了。** 他最后那句是："让你做个独立页面给我看预览样式，为什么不做？为什么要直接改项目？"

[素材] **意象是免检的，事实不是**：给「归墟」配图标时，推演链是"归墟 → 百川汇流 → 航海 → 罗盘 → 领航员"。每一步都说得通，合起来全是空的——**这些意象跟项目一点关系都没有**。用户质问："为什么你会一直盯着罗盘，海，领航员，这种意象来说？这与我们的项目就这么贴合吗？"换成"从项目自身出发"之后，八瓣收拢的图形一次就对了。

[素材] **"一键搞定"要先数前置条件**：项目按 Docker 容器化规划了很久，直到有人问一句"用户下载我们的项目，他电脑里需要有 docker 吗？"——**"一键"的第一步是装 Docker**。加上"启动后打开个网页？？我接受不了"，方案整个转向桌面应用。**推翻一个方案，理由可以是"形态不对"，不必是"技术不行"。**

[素材] **威胁模型决定架构**：单用户本地场景里，PG 的 RLS 是唯一真正的损失——它换不掉一个常驻进程（要起、要停、要占端口、要设密码、要备份目录树、崩溃了会残留）。判断的落脚点是那句：**"这个项目的威胁模型是「工具自己写错」，不是「恶意用户绕过权限」。"** 一句话把 RLS 定性成过度设计。**安全方案该按威胁模型选，不是按"它更专业"选。**

[素材] **"只做 Windows"和"写死 Windows"是两件事**：前者是排期，后者是债务。实测整个项目的 Windows 绑定只有三处——`charts.py` 的字体名、数据目录硬写 `%LOCALAPPDATA%`、`desktop.py` 的 `gui="qt"`。**三条加起来不到十行，决定了三年后还能不能上 mac。** 而"不打包浏览器、用系统自带的那个"本身就是跨平台思路：WebView2 / WKWebView / WebKitGTK 是同一套 pywebview API。

[素材] **归类不是减少数量，是给每类定同一套规矩**：工具按性质分四类——读（幂等、不用确认、返回数据）/ 写（要确认 + 走业务规则 + 事务）/ 结构（要确认 + 先落快照）/ 产出（读数据 + 落文件，不改数据）。同类不必是同一个工具（确认形态差异大的可以分开），但**同类守同一个规矩**。

[素材] **失败不要写"建议"**：工具报告事实，不替模型想下一步。模型拿着"你该试试 XXX"会照做，而它本可以自己判断得更好——**给它事实，别给它结论。**

[素材] **一致性 > 省事**：确认弹窗为什么不"分场景"（简单的留对话内、复杂的弹起弹窗）？因为那样"确认"会一会儿在这儿、一会在那儿，**用户不知道该看哪**。统一成两种固定形态：底部弹窗（当场交互）+ 对话内缩略卡（事后留痕）。

## 二、排查 —— 怎么找到的

[素材] **Markdown 渲染**：中文标点让 `**粗体**` 失效——根因是 CommonMark 的 flanking 规则为英文设计（依赖"词间空格"，中文没有）。最省时间的一步是**对照实验**（marked vs markdown-it 结果一模一样 → 停止怀疑实现，去看规范）。详见正文。

[素材] **服务进程**：「健康检查 200」≠「代码是新的」。判断代码真生效只认一条：`worker 启动时间 > 代码文件修改时间`。排查进程要看**全树**（占端口的可能只是 wrapper）。详见正文。

[素材] **PG 事务中毒 vs DuckDB 宽容**：DuckDB 的 `try/except pass` 能用，PG 上会让整个事务废掉（`InFailedSqlTransaction`）。修法是每次尝试包 `SAVEPOINT`。DuckDB→PG 迁移最隐蔽的坑之一。

[素材] **`trace.tools` 用 `[-1]`**：pending 轮次没有 `add_assistant`，取 `[-1]` 会拿到上一轮数据。正确做法是"**记录调用前的长度，只看之后新增的**"。

[素材] **状态筛选歧义**：模型把"已结算"理解成 `status_raw` 精确匹配，漏掉了"已结算已下证"。修法：在 SCHEMA_DESC 里明确"status_raw 是组合状态"，prompt 里引导优先用布尔字段。

[素材] **会话内存缓存会覆盖磁盘修改**：`_sessions` 字典缓存着已加载的会话，直接改磁盘文件后内存里还是旧的，下次 `save()` 原样覆盖回去。清缓存只能重启进程。

[素材] **「到处都在」≠「用了很多次」，而是「抄了很多份」**：换主色时以为改一个变量就够了，结果界面还是有蓝的。`grep` 全部十六进制色值才看清——品牌名的蓝紫渐变、罗盘的四色、光点的 rgba，是**三套各自独立的硬编码**。视觉上的"主色渗透在各个角落"，技术上的真相是同一个色值被复制到了四处。**改色只是手段，清掉"同一含义的多份副本"才是。**

[素材] **"说不出哪里不对"是最值钱的线索**：重做工作台那次，用户反复说"有种莫名其妙的压迫感""灵感枯竭了，想不到问题点，只剩没法说明的感觉，这咋办"。一路追下去，根因是**色温**——不是光效、不是线条、不是字体。调完他说"压迫感骤降，没那么冷了，**色温真好用啊**"。**"说不出"不等于"不存在"，它只是还没被翻译成一个变量。**（对比上一次：那次"说不出的丑"追到的是**光效过载**——两次都证明，"感觉"是能定位的，只要肯停下来追。）

[素材] **成败靠"猜"**：旧代码用 `_is_success` 判断工具返回，逻辑是"有没有某个键"——结果把 `not_found` 判成了成功。改成统一直读 `ok` 字段。**约定一个字段，比推断结构可靠。**

[素材] **动作记忆的三个 bug**（同一个毛病：记了，但记的是没用的东西）：
① 只记"调过哪些工具"，**结果全丢**——模型知道做过，不知道做出什么
② 把每次工具返回的 8000 字符截断版存进会话文件，**文件越滚越大**
③ 参数按位置截前 3 个——`list(args.items())[:3]` 会把 `table_name` 切掉

[素材] **中断的那一轮没进历史**：`run_agent` 只在最终回答时调 `add_assistant`，而写操作（增删改）是**中断**的——走不到"最终回答"。所以用户点头、执行完，模型回头看自己的历史，**那一轮是空白的**。

[素材] **压缩检查放在循环外**：单轮巨任务（一个回合里烧掉几十万 token）完全绕过压缩判断，因为它只在"轮与轮之间"看一次。**安全检查放在循环外，就等于对最长的那一轮不设防。**

[素材] **`dispatch` 无参数防御**：工具分发表对入参没有任何校验——多传、少传、类型错，**都击穿整轮**（不是返回错误，是整轮崩掉）。

[素材] **熔断要按 (工具 + 参数) 计数，不能按工具名**：按名字计，会把"换参数探索"误杀成"思维死循环"——**它明明在往对的方向试。**

[素材] **隔离层会把底表的默认值吞掉**：加上软删除隔离（视图 + `INSTEAD OF` 触发器）之后，`INSERT INTO inventory (sku)` 本该让 `qty` 用 `DEFAULT 0`，实际报 `NOT NULL constraint failed`。

根因：**视图的 INSERT 触发器是显式列列表**——`VALUES (NEW.id, NEW.sku, NEW.qty, …)`。没给的列在 `NEW` 里是 `NULL`，原样传下去，**底表的 DEFAULT 永远轮不到生效**。

修法：生成触发器时，对有默认值的列用 `COALESCE(NEW.col, 默认值)`；默认值还是从 `PRAGMA table_info` 读，不新增第二份。连带一个错误分类的问题：`Duplicate`（换个值再试）和 `ConstraintFailed`（少给了东西）**处置方式完全不同**，不能都报 `duplicate`。

**教训：每一层抽象都会遮住下一层的某个特性。** 隔离层挡住的不只是已删的行，还有默认值、约束这些"数据库本来就管得好"的东西——**而且它不报错，只是悄悄地让那个特性失效。**

## 三、认知与洞见 —— Agent 和自己

[素材] **"这个项目的问题不在某一处，在没有主线"** —— 一个能跑、评测满分、却让人"感觉模糊"的项目。模糊不是技术问题，是**主线缺失**。

[素材] **僵尸的元观察**：所有僵尸出自同一个习惯——"**每次重构只搬新、不扫旧**"。DuckDB→PG 的过时提示词、轨迹搬家的旧 CSS、workflow→Agent 的 `legacy/`、多 tab→单 tab 的残留按钮。**要治的是习惯，不是清单。**

[素材] **"没有表定义"这句话我说错了** —— 项目里其实有（`schema_store.get_table_schema`），只是散成三份（建表用的 `TABLE_SCHEMA`、读结构的 `describe`、存中文的 `schema_meta.json`），而且缺主键和关系。真正的病不是"没有"，是"**三份、互不知道、没有权威**"。

[素材] **无效旋钮**：`agent.tool_result_limit`（默认 8000）在设置页看着像"控制给模型的 token"，实际只截"推给界面"的副本——**模型吃的是全量**。用户调它，一点用没有。这类"**描述和实际对不上**"的参数，比没有更坏。

[素材] **"功能""工具"都太粗**：一次对话里逼出来——日志是"机制"不是"功能"；关系是"数据"不是"工具"；RAG 是"子系统"不是"工具"。三个词都被滥用了，把"动作 / 数据 / 子系统"搅成一锅。判断一个东西是什么，先问"**谁发起、谁消费**"。

[素材] **"中断"是一类机制**：澄清、选择、确认——原本散在三处（提示词 / 工具检测 / pending）。统一后是：中断 → 存成 todo（落盘）→ 展示 → 用户回复 → 断点续跑。**A1 从"赌模型记得问"变成了机制。**

[素材] **一个工具，两个用途**：`ask_user` 同时覆盖了原本的 A1（意图澄清）和 A2（方向选择）——有 `options` 就是选，没有就是问，自由输入框永远在。**"选项是帮你省事，不是限制你说什么"。**

[素材] **图形是名字的证人**：用户一度想放弃「归墟」（觉得不贴合，考虑启明星 / 北极星 / 星盘），理由写得很清楚——"我们的项目主题，图标，名称，应该是三点一线，保持协同性"。**名字靠不住，是因为没有图形能证明它。** 八瓣收拢的图形做出来之后，他改口："归墟，是我们新的，也是最终的名字。"

[素材] **一个词捆着三样东西时，先拆词，再谈方案**："向量库"让人以为它是一个柜子，其实是**切片原文 + 向量 + 索引**三样捆在一起。拆开之后架构立刻清楚了：原文归 SQLite（唯一真源、要事务），索引归 FAISS（派生、可重建）。**跨存储没有事务，所以真源只能有一个。** 这条判据能替掉一大半架构争论。

[素材] **"没人会用" ≠ "没人会看"**：我一度把"这个项目不会有人 clone 下来跑"读成"这项目没有读者"，据此认为 README 和设计文档可以马虎。用户纠正了——写这些都是为了他自己，但他要拿它去求职：**不会有人用它，但会有人看它。** 这两件事差得很远：前者让"安装向导、跨平台适配"可以粗，后者让"README、设计文档、代码整洁度"变成交付物本身。

[素材] **"想记录"和"该留在代码里"是两件事**：`legacy/` 里躺着项目早期 workflow 架构的实现，它 README 写着保留理由是"面试时可展示我做过两种架构"。听起来成立。但用户否了："这是过去的错误决策，如果想记录，完全可以记到博客素材里……没必要留在代码里污染。"——**要留的是判断，不是尸体。** 而且那个判断早就在素材库里了，留代码是纯冗余。

[素材] **记忆和存证是两件事，`session.py` 一肩挑两**：这是它"又乱又漏"的根。**记忆**是给模型的（要精炼、要控制大小），**存证**是给人的（要完整、不怕大）。混在一个文件里，两边的需求互相拉扯——想给模型省 token，就伤了人的存证；想给人留全，就撑爆模型上下文。

[素材] **别把对话压成散文**：旧做法是"把一段对话揉成一团话"，问题是**散文的信息不可控**——该留的被挤掉、不该留的占地方。方向是"**从对话里留下事实**"，不是"把对话揉成一团话"。

[素材] **动作凭据只浓缩、不删除**：工具调用记录可以摘要，但不能删——**删了，模型会谎称自己没做过。**

[素材] **续跑的正解：把"用户确认 + 执行结果"伪装成那次工具调用的返回**：喂回模型时让它**始终站在同一条线上**——它知道自己刚才在做什么、结果是什么。这样它不会把"用户确认"误解成一条新指令。

[素材] **guard 卡错了位置**：安全检查现在卡在 `nl2sql` 里面，只罩得住"模型写 SQL"这一条路——服务拼的 SQL、DDL，全绕过去了。正确位置是**执行前**：所有 SQL 出门前都过它，不管从哪来（模型写的 / 服务拼的 / DDL）。

[素材] **不合规不要抛异常**：拦下来 + 返回 `{ok:false, error_type:"security"}`，让模型看得懂、能换条路走。**抛异常会击穿整轮**——一个越界查询不该让整个对话崩掉。

[素材] **audit 必须和"改库"在同一个事务里**：现在它是追加写文件，**不原子**——改成功但审计失败 = 没账；审计写了但库没改 = 假账。所以 audit 该进库（业务凭据），trace 留文件（观测日志）。**性质不同，去处不同。**

[素材] **能力清单：一处来源，处处遵守**：把"这套配置认什么"集中成 `capabilities`（`tool_calling` / `reasoning_echo` / `context_window`……），别处按它办事。填上 `reasoning_echo: false`，编排层就不再硬塞回传了——**一个 400 的雷直接拆掉。** 附带收获：`context_window` 正好治压缩阈值硬编码 `500000` 的账，改成"用到 70% 就压"，换模型自动适配。

[素材] **靠分类，不靠分级**：设置页原来的 `normal / advanced` 分级是按"改坏了多严重"分的——**那是给维护者看的**；用户找东西靠的是"这是哪一类"。所以取消分级，改按用户会怎么找去分：模型 · 展示与确认 · 数据保留 · 上传。

[素材] **给数据，别给结论**：把 `query_database` 的返回从"一段自然语言答案"改成 `columns + rows + status` 之后，有件事没预料到。问"王五负责的项目有几个"，模型拿到 `status: empty` 之后**自己决定再查一次**（"列出所有负责人去重及各自记录数"），然后回答"0 个，现有分布是张三 4、李四 3、赵六 3"。旧流程下它只能转述"共 0 条"。

**`status: empty` 和 `status: ok` 分开，等于告诉模型"这是真的没有，不是查错了"**——它于是会自主核实，而不是把一句话递给你。**给结论，模型就到站了；给数据，它才知道还能往哪走。** 同一次改造还省掉一次 LLM 调用（旧流程里 `summarize` 专门负责"把数据翻成人话"）。

[素材] **作品集不该抄样式**：想直接参考 Codex / Claude Code 的确认卡片——但它们本质是**终端**（文本+按键），项目是 **WebUI**（图形卡片），样式不通。更重要的是：**评审看的恰恰是"你的设计"，抄了等于交白卷。**

[素材] **运动 ≠ 发光**：深色界面看久了累，第一反应是"这是深色的弊端"。但把全站数一遍——**12 处装饰性发光，其中 2 处是永不停止的循环动画**——真相就出来了：不是深色，是**把发光当装饰**。区分是：**运动**（旋转、位移）表示"活着"，不疲劳、甚至必要；**发光**（glow / blur / shadow）照亮周围、抢注意力，**只有报状态时才配存在**。更细一层：疲劳的具体来源是「发光半径的脉动」——`drop-shadow` 从 3px 变到 9px，周围一圈都在变亮。**雷达上的光点是明灭，不是泛光。**

[素材] **雾感 = 把黑提成灰**：砍完发光之后，用户又推深了一层——「辉光是雾感的来源，让整体显得脏，这是丑感的根本。可以亮，但尽可能解决辉光散射」。机制是：`drop-shadow` 在元素周围铺一圈半透明色，**那一圈的黑被提成了灰**，于是黑不够黑、亮不够亮，中间全是雾。**同一个机制项目里早就写过一次**——全局噪点的注释：「feTurbulence 出的彩色噪声，叠在暗场上会把黑提成灰，压到 0.016 才不至于把底子弄脏」。关键区分：**要"亮"就用元素自身的色值，不要用阴影去造光。** 典型的反面教材是欢迎屏那个光点——实心点外面套了一个 `r=3.4`、`opacity:.26`、`blur(1.8px)` 的圆，纯粹为了造"发光"错觉。**删掉它，点还在，雾没了。**

[素材] **质感和光是两件事（一次误删换来的判据）**：顺着上一条去"光感"，我把罗盘和品牌名的所有渐变一刀切删了。结果用户反馈："改错了，质感改没了——要处理的是光，不是质感"。区分其实很清楚：**渐变填充（色块内部的色彩过渡）是质感；模糊半径（元素之外的晕）才是光。** 芒尖拆成受光面/背光面是质感；在它外面套一个 `blur(1.4)` 的辉光是光。品牌名的四段渐变是质感；它的 `drop-shadow(0 0 13px)` 才是光。**判据：带模糊半径的才是光。** 于是 32 个芒尖面、4 个核心渐变、10 个渐变定义全部恢复，只保留删除辉光/泛光/模糊高光。**症状也不一样：删掉光界面变干净，删掉质感界面变单薄。** 这条判据现在写进了设计语言规范。

[素材] **思维熔断设计**：不是压制 agent 的怀疑，是给怀疑一个出口（hint 验证）和终点（成功调用上限）。实测：空结果场景从 4 次调用降到 1 次。

[素材] **异常熔断实测**：prompt 引导（"不要反复重试"）**先于**程序熔断生效——agent 2 次失败后自己止损，没触发熔断阈值。两层机制的理想状态是"第一层先拦，第二层兜底"。

[素材] **A2 分叉管理**：用户说"已结算"有两种合理解读（包含匹配 141 vs 精确匹配 76）。系统检测到这种天然歧义时，**两个分支都展示**，让用户自己判断——比"触发澄清"更高效（省一轮交互）。

[素材] **思考链的语言控制**：加一句"思考也必须用中文"，中文占比从 12% 升到 62–71%。但**加强措辞没有正收益**（"【强制】禁止英文思考"反而降到 75%）——**别过度施力**。


[素材] **`ask_user` 不是新机制，是确认卡片的泛化**：一度把它们当成两种中断（一个弹窗、一个卡片），准备各写一套。LangGraph 的 `interrupt()`、Cline 的 `ask` 消息、MCP 的 elicitation 都在做同一件事——**工具挂起 → 用户回应 → 工具拿到回应继续**。于是统一成一个模型：`ask_user` 的续体是「答案就是返回值」，确认卡片的续体是「执行完才是返回值」。**差别只有两点：问题谁写的、回答之后做什么。** 少写一套机制，也少一处会漂移的地方。

[素材] **确认卡片本来就在这条路上，只是断头了**：它一直有"拿到用户回答"的能力，但拿到之后自己执行、直接给用户一句话，**没有把结果还给模型**——模型那边是断线的。所谓"接入续跑"不是新接线，是把断掉的这截接上。改造后确认后的反馈从模板文案变成模型自己组织的话，代价是每次确认多一次 LLM 调用。**这个代价买的是"模型知道刚才发生了什么"。**

[素材] **断点存"这一轮已经发生过的消息"，不存 system 和更早的历史**：它们每次都能重新组装（system 由代码拼、历史在 session 里），存进断点只会和 session 重复，越滚越多。存下来的是 `assistant(tool_calls)` + 已完成的 `tool` 结果 + 挂起调用本身——**刚好够让模型站在同一条线上**。还有一个坑：同一批 tool_calls 里排在挂起位置后面的，不能直接丢（assistant 里列了它们，缺了 API 会报错），要显式补一条「因前一个操作需要确认，本次未执行」。

[素材] **写操作 `affected` 恒为 0（视图 + INSTEAD OF 触发器）**：更新一条记录，数据确实变了，但 `cursor.rowcount` 报 0——因为写的是业务视图，真实改动发生在触发器里的底表，游标认为自己一行都没改。模型据此判断"没改成"，转头再查一遍。**这是"隔离层做得越干净，上层越看不见它"的代价。** 正解是 `total_changes` 的差值：它把触发器内的改动也算进来。同一个坑 DELETE 也踩，只是先被 UPDATE 暴露出来。

[素材] **"用户的问题为什么发了两遍"**：`api.chat` 在轮次开始时 `add_user`，`run_agent` 又 `append` 了一条同样的 user——每轮模型都看到两遍同一个问题。这是重构时两处各加一次留下的。**续跑改造必须把它修掉**：续跑时"确认"不能进 user 历史（它不是新问题），而中断轮的问题已经在历史里。一条规则：**user 消息只在 api 层写一次，run_agent 只管读。**

[素材] **视图软删除的隐藏成本：`describe()` 的旧签名**：`nl2sql.get_schema` 还按老接口 `describe(table)` 调用，而 `storage.describe` 早改成了 `describe(con, table)`。正常查询走的是 `ctx.schema`（另一条路），所以一直没暴露；**恢复记录**这条冷路径一调就炸——"missing 1 required positional argument: 'table'"。判据：**重构换了签名，冷路径不会自己报错，只会等到有人踩。** 顺手把它改成复用 `schema_store` + `render_schema`，和别处同一个转换点。

[素材] **未解决的中断占输入区的位置，不浮在对话流里**：确认卡片原来挂在某一轮下面，用户得在对话里找；`ask_user` 又需要一个弹窗。如果两个位置并存，用户永远不知道"要回应的东西"该看哪。现在**未解决 = 底部弹窗（占 composer 的位置，输入区收起），已解决 = 对话流里一行缩略**。两种长相，同一个容器；屏幕上永远只有一个能打字的地方。

[素材] **"已解决"的卡片刷新后就没了**：`confirm` 是运行时状态，活在 turn 对象上；会话文件只存 messages，刷新重放时卡片不存在。设计里说缩略卡是"事后留痕"，现在只在当前会话里成立。**这个缺口留到交互层**（恢复页/历史重做时一起补），不在工具层临时打补丁。

[素材] **报告不是"统计功能"，是"排版功能"**：旧报告把软著表的四个日期列、负责人、分类编在 `stats.py` 里，换一张表就整块作废。一开始想的是"把统计通用化"——加 `date_column` / `group_by` 参数。但那只是把一套业务形状换成另一套：遇到两个维度、或者"按周分桶"，参数就表达不了。**真正的分界是：统计是模型的事（它已经能查、能算），报告工具只负责把结果画成文档。** 于是接口变成 `title + intro + sections`，文字、表格、图表都由模型给形状。工具不再认识任何字段，**也不会因为数据源变了而重写**。

[素材] **合并两个工具时，参数形状也要合并**：`create` 和 `batch_create` 合成一个，起初想保留 `record`（对象）和 `records`（数组）两个可选参数，谁给用谁。但那就是把"两个工具"换成了"一个工具里两条路"——模型仍要判断这次算哪种，实现里仍有两个分支。最后定为**单条也传数组**：一个工具只有一种形状，执行端只有一个事务分支。**省下的不是代码行数，是"两套行为会不会不一致"这个问题本身。**

[素材] **压缩不该删消息，只该推进一个指针**：旧 `compact()` 最后一句是 `self.messages = recent_messages`——给模型省 token 的需求，把"用户能回看的对话"一起吃掉了。用户刷新后，早期记录直接消失，而且没有任何提示。现在 `messages` 是**存证**（只增不减），压缩只推进 `summary_upto`：**模型看到的历史变短了，人看到的一点没少。** 同一个列表里放两件需求相反的东西，迟早有一方吃掉另一方。

[素材] **摘要的输入里必须带动作凭据**：只把"用户说 / 助手说"的正文喂进摘要，模型会丢掉"当时调过什么、结果是什么"，之后回看就会否认自己做过。设计里那句"动作凭据只浓缩、不删除"不是留给人看的——**它是给模型的下一次判断用的**。所以压缩时把 `[query_database → 成功，3 行]` 这类行一并喂进去。

[素材] **回放要看的不是 raw，是四个字段**：旧版把每次工具返回的前 8000 字符整段塞进会话文件，一轮五个工具就是几十 KB，而九成是模型当轮已经看过的数据。真正会回看的是：一句结果要点（`gist`）、模型写的 SQL、产出的文件、前几行数据。所以 `gx_tools` 存 `{gist, sql, file_path, preview}`，`raw` 只留在当轮推给界面的事件里。**判据不是"要不要留返回内容"，是"三个月后回看时，你到底会看哪几行"。**

[素材] **"结束了"和"记得结束了"是两件事**：超时、熔断、到上限，以前都是直接 `return` 一句话就完了——用户看到了，历史里没有。下一轮再问，模型完全不知道自己刚才做过什么，于是要么重新做一遍，要么说"我没做过"。**收尾必须回写**，不管这个结尾是"成功"还是"被迫停下"。所有退出路径收进一个 `_end()`，就不会再有哪条路忘了。

[素材] **`error_type` 是工具返回的一部分，不是异常**：安全拒绝以前抛 `SecurityError`，一路冒到 api 变成"出错了"——用户看到一句冰冷的话，模型失去了换条路的机会。现在 `dispatch` 拦下来，返回 `{"ok": false, "error_type": "security"}`。**同一个道理适用于参数错误**：模型多传一个字段、少传一个必填，`TypeError` 会把整轮击穿；拦成 `invalid_arguments`，它下一轮就能改对。

[素材] **SQL 层不该偷偷自修正**：`nl2sql` 里原来有一层"执行失败 → 让 LLM 修 SQL → 再执行"，最多两次，外面 agent 还有一层熔断。问题是**模型看不见这层修正**——它以为自己的查询一次就成了，如果修出来的结果语义变了，它也不知道。删掉之后，SQL 错就作为一个失败的 `query_database` 返回，模型自己决定换 SQL 还是换问法。**错误暴露给模型，比在工具内部消化更有价值。**

[素材] **"成败"要有个明确的字段，不能靠猜**：旧 `_is_success` 用 `"error" not in data` 判断——`{"status": "not_found"}` 这种没有 error 的返回会被判成功。工具层现在统一带 `ok`，编排层只看它。同类的坑还有安全拒绝：判的是 `is_security`，而工具从来没返回过这个字段，于是安全拒绝一直被当成普通失败，既触发熔断，又误导模型去改一个根本不存在的 SQL 问题。**判定字段和实际返回对不上，比没有判定更糟——它看起来在工作。**

[素材] **"填了才带"是碰运气，"认才带"才是规则**：`reasoning_effort` 一直靠"用户没填就不带"躲 400——可换个模型、用户在设置里填了，照样炸。能力清单把"这套配置认什么"收成一处：预设打底、卡片可覆盖、默认保守。编排层回传 `reasoning_content` 前问 `reasoning_echo`，带参数前问同名项，**同一个判断不再散在三个 if 里**。

[素材] **压缩阈值不该是常数**：`500000` 写死的时候，换一个 32K 窗口的模型，压缩永远不会触发——请求先撞上限 400 了。改成 `context_window × 比例` 之后，同一个设置在任何模型上都成立：**窗口是模型的属性，比例才是人的偏好。** 这也顺带解释了为什么"能力清单"该在模型层：它是模型层的属性，别的层只读。

[素材] **闸门的表名白名单，防的不是「写错」**：一开始想的是「表名写错 SQLite 会报错，不用管」。但白名单真正拦的是**绕过视图直接打底表**——`orders_all` 是物理表，SQLite 认为它完全合法，模型只要写出这个名字，就能看见并改掉已删除的行。**隔离层是视图，而视图对"直接叫底表名字"这件事没有防护。** 列名不校验是另一个判断：写错的列 SQLite 会报 `no such column`，模型看得懂；全量校验要处理别名、表达式、JOIN 作用域，收益不抵复杂度。

[素材] **「解析不了」不等于「不安全」**：旧闸门的判据是「sqlglot 解析失败 → 拒绝」。于是一个完全合法的复杂 SELECT（模型想把总数和明细一起查回来）被「无法解析」拦掉，模型只能换个简单问法。**解析器认不认识这条 SQL，和这条 SQL 想干什么，是两件事。** 现在解析失败时看关键字：开头是 SELECT、不含写操作词，就放行。判据要贴着意图，不能贴着工具的能力边界。

[素材] **特权旁路要有名有姓**：恢复已删行要打底表、要改 `is_deleted`，这在闸门眼里和"绕过隔离"长得一模一样。所以 `system=True` 不是"关掉检查"，是**一句明确的话**：这次操作是系统内部的，不是模型发起的。旁路只跳过表名和系统列，语句类型照查——**能放宽的只是"谁的表"，不能放宽"想干什么"**。

[素材] **审计必须和写入同生共死，所以它得进同一个事务**：以前 `audit.log` 是追加写文件——改库成功但审计失败 = 没账；审计写了但库没改 = 假账。改成表之后，`record(tx, ...)` 收的是事务句柄：**提交时两张表一起落，回滚时一起没**。这不是"顺便记个日志"，是"账本和库是同一份事实"。导出和清理没有事务可依附，才退回自己开连接。

[素材] **系统表不进白名单，是对的**：`_gx_audit` 建好之后第一次被闸门拦下来——"这些表不在数据源里"。这不是漏洞：**模型本来就不该看见审计表**。要读它得显式 `system=True`——和恢复已删行是同一种旁路。**看不见的东西才是安全的；拦下来的报错是在提醒"你走错路了"。**

[素材] **设置页按「用户会怎么找」分组，不按「后端模块」**：`llm / agent / display / safety` 是代码的目录结构。用户想改「删除的东西留几天」，不会想到去 safety 组——他想到的是「数据保留」。分组一旦跟着代码走，用户每次都要先理解一遍你的模块划分。**设置页是给用户的，不是给维护者的索引。** 同理，`normal / advanced` 分级按「改坏了多严重」——那是维护者的判断，不是用户的找法。改成「开发者模式」一个开关，内部参数整组藏起来，比在每个参数旁边挂一把锁干净。

[素材] **快照清理写了，但从来没被调用**：`snapshot.cleanup(con, days=30)` 在测试里跑得好好的，生产路径里一次都没接——启动时只清了软删行。这类「功能存在但入口没接」比没写更隐蔽：代码在、注释在、测试过，所以没人会去查它到底跑没跑。顺手接上之后，保留期和开关才真正有意义。**判断一个功能在不在，不要看函数在不在，要看它有没有被调用。**

[素材] **保留期是两种东西，不是一个数字**：软删行 7 天、快照 30 天。一开始想用一个「数据保留天数」对付过去，但它们的重量不一样——快照是一整套结构和数据，删了就没法回头；回收站里的一行删了只是少一条记录。**同一个词（保留）在两个尺度上，不该共用一个刻度。** 所以拆成两个参数，再加一个快照专属的自动清理开关。

[素材] **存证挂在哪条消息上，取决于「什么时候读得到」**：确认卡片的终态一开始想写进最终那条 `assistant`——毕竟 `gx_tools` 就在那儿。但续跑途中又中断一次时，`_end()` 还没走到，assistant 那条根本不存在；这时候刷新，已经答过的那张卡会连同「还没写」的回答一起消失。改挂到本轮开头那条 `user` 上就没有这个空窗：**一条消息该不该承载某种数据，不只看它"是不是这件事的结果"，还要看它"在需要被读到的时刻存不存在"。**

[素材] **一轮里可以中断多次，所以卡片是列表，不是字段**：先问口径、再确认删除，是同一轮里的两次中断。旧实现 `turn.confirm` 只有一个字段，第二张卡一来就把第一张顶掉——实时界面上就已经在丢历史了。做回放时才看清：**如果只在回放里"和实时保持一致地丢信息"，那不是一致性，是把 bug 一起归档。** 改成数组之后，实时和回放都留得下。

[素材] **终态从工具的续体返回判，不从用户那句话猜**：判断「这次是执行了还是取消了」，最直接的想法是看用户输入是不是"取消"。但导入那一路的取消是模型解析出来的（"不用了，先按台账来"也能是取消），按词表猜必漏。续体返回里本来就有唯一答案：取消统一是 `error_type: cancelled`，其余是执行结果或 `ask_user` 的答案。**已经被下游判过一次的东西，不要在上游再猜一遍。**

[素材] **「可点开回看」决定了要不要存详情**：`gx_tools` 的教训是不存 raw——回看时没人看那 8000 字符。但缩略卡不同：设计里它明确写着"可点开回看候选 / 差异"。既然有展开这个动作，候选行就必须存；只留 `affected: 3`，展开就是一个空壳。**存不存的判据不是"数据大不大"，是"界面上有没有一个动作会去读它"。** 这条反过来也成立：没有展开动作的字段，一行都不该存。

[素材] **同一句话在一个头里出现两次**：已解决卡片的标题是「删除 166 条记录 · 已执行」，旁边还有一个 scope 标签写着「删除 166 条记录」。两个值各自都"对"，但因为标题里已经拼了 scope，拼出来的头就重复了。标题只说状态、scope 交给标签之后：`已执行｜删除 166 条记录`，信息一点没少。**拼装文案的地方和展示的地方都觉得自己在说完整的话，合起来就是废话。**

[素材] **取消一次确认和跳过一次提问，不是同一种收尾**：两者在界面上都是「取消」，一开始也共用一个续体——`{ok: false, error_type: "cancelled"}` 喂回模型。但结果不一样：取消删除时，模型知道「用户拒绝了」，可以接着说「好的，没删」；跳过一次 `ask_user` 时，模型手里**没有答案**，它会拿猜测或者一句「那我先停在这里」凑一段回答——而界面已经写着「已跳过」，那句话纯属多余。所以跳过提问不再续跑：清挂起、当场收尾。**同一个按钮，在不同中断里意味着不同的事：一个是"拒绝这个动作"，一个是"撤回这个问题"。** 收尾那句话也不是模型说的，落盘时标 `gx_notice`，界面画成警告条而不是正文——**排版也是一种归属声明：用正文的样式说系统的话，读者会以为是它自己的回答。**

[素材] **工具行是前端画出来的，历史里没有**：挂起的工具调用在 `dispatch` 返回之前就抛了，`tool_log.append` 永远走不到。实时界面上那一行看起来一切正常——它是前端收到 `pending` 后把「待确认」改成「成功」画的——直到刷新才露馅。补法是在续跑时用断点里的 `call` / `args` 加上续体结果补一条；跳过的路径没有续跑，就在写警告时一并补。取消的那条标 `cancelled` 而不是留 `ok: false`，否则回放会画成一枚红色的「失败」，而用户明明只是说了「取消」。**界面上的状态如果不是从存证里长出来的，它只活到下一次刷新。**

[素材] **入口不同，执行端不该有第二套**：恢复页是人在页面上点的，对话里模型也能恢复——一开始很容易顺手在接口里写一段"页面专用的恢复 SQL"，因为那样最省事。但那段 SQL 会漏掉审计、漏掉软删规则，然后两边的行为就开始分叉。做法是把页面当成另一个调用方：`/recover/restore` 里调的还是 `execute_restore`，`/recover/rollback` 里调的还是 `execute_structure`。**一个动作的实现只能有一份；入口决定的是"谁在按"，不是"按下去发生什么"。**

[素材] **快照留着，表可能已经删了**：版本历史按表分组，可库里那几张表（projects / inventory）早就被删了——快照还在。第一反应是"没有表的快照不该显示"，但那恰好把这些快照存在的意义删掉了：删表前落快照，就是为了哪天能把表变回来。所以接口给每组一个 `exists`，界面标「表已删除」，确认框里再加一句「回滚会把它重建出来」。**数据存在，和它所描述的东西还在，是两件事；界面要把这两件事分开说。**

[素材] **一端声明、两端显示，但只存一份**：关系最容易的实现是"加一条时写两行，A→B 和 B→A 各存一份"，这样两端查询都简单。代价是两份数据会漂移——删了一端忘了另一端、改了基数只改一半，而这种不一致往往要等用户切到对面的表才发现。现在库里只存声明的那个方向，`/schema` 读取时按表摊成"出/入"两份给界面。**同一事实存一份，需要另一种视角时在出口处转换，不要在入口处复制。**

[素材] **一个页面上可以有两种保存节奏，前提是它们各自说得清**：数据字典页原本是"草稿 → 保存 → 离开拦截"，为中文名设计。关系加进来时，第一反应是把关系也塞进草稿，但那意味着跨表同步、双向删除和一份更长的 diff——为的只是让页面"看起来统一"。最后关系改成加/删立即落库，中文名的草稿流程一个字不动。**一致性的目标是用户不会误解，而不是所有东西都走同一条管道；只要"这一下已经生效"和"这一下还没保存"在界面上分得清，两种节奏可以并存。** 关键是加完只重取关系、不整份重载——否则一次立即生效会把旁边还没保存的草稿一起冲掉。

[素材] **多问题的答案必须带着问题回去**：`ask_user` 从单问题扩到 1-3 个时，最省事的做法是续体返回一个字符串数组，按顺序排。但模型拿到 `["orders", "按月"]` 之后要靠位置去对——它上一次看到的参数里有几个问题、顺序是什么，中间还隔了一轮推理，对错一位就是静默的错误。现在每条答案是 `{question, answer}`：**结构里带上足够的上下文，读者就不需要记住位置。** 顺带一个形状决定：单问题也传 `questions` 数组，和 create 那条一样——一个工具一种形状，模型不必猜这次是哪种。

[素材] **一行日志把一整轮打翻**：Windows 控制台是 GBK，模型给的参数里出现 `↔` 这类字符时，agent 里那句 `print(f"[工具] {name}({args})")` 抛 `UnicodeEncodeError`，顺着调用栈冒到 api 的兜底 except，用户看到的是「出错了 'gbk' codec can't encode character」。**日志是旁路，不该有能力中断主流程。** 修法不是给那一句加 try（下一句照样会炸），而是在进程启动时把 stdout/stderr 设成 `errors="replace"`——编不出来的字符变成 `?`，日志难看一点，对话照常。判断"这个错误归谁管"时，先看它发生在哪条路径上：日志路径上的错误，就该被日志路径消化掉。

[素材] **配置文件是化石层，判断死活的唯一标准是"谁在读它"**：`config.yaml` 里的 `data.excel_path` 活过了整个数据层重写——因为启动导入的 `ingest.py` 删掉之后，没有谁再去 grep 它，而「关于」页还留着一行 `初始数据源` 在展示它。同一条 `data` 段里的 `table_name` / `db_url` 是 PG 时代的，连展示都读不到，页面上就变成三行永远为空的值。**删掉一条管线时，要连它的配置键一起删；判断键死没死，不看它还在不在文件里，看还有没有代码读它。** 症状很好认：一个只出现在展示层、从不影响行为的配置项，基本就是上一代留下的。

[素材] **必需的文件才需要模板，模板本身是个税**：`config.yaml.example` 存在的唯一理由是 `config.yaml` 被当成启动的先决条件——`load_config` 没有兜底，文件不在就 `FileNotFoundError`。于是每个新克隆都要先复制一份，而这份模板只写了两个键（实际设置页会写二十多个），既过时又误导。把「读不到就是空配置、默认值在注册表里」补齐之后，模板没有存在意义，删掉反而少一个会撒谎的文件。**默认值完整的地方，不需要示例文件；需要示例文件的地方，说明默认值没补齐。**

[素材] **评测的期望值不能是"当时那个数"**：旧题库的 `expected_answer_contains` 是照着当时那份 Excel 硬算的——"已下证的项目有几个"期望 `["23"]`。数据一换，全部失败，而且失败的原因跟代码无关。新版把期望改成**现场算**：fixture 灌完之后，用独立 SQL 算出 `status = '在用'` 是 6 台，再拿这个 6 去比回答。**期望值应该由"当前世界的事实"推导，而不是由"上一次世界的快照"记忆。** 题目和覆盖面才是资产，数字不是。

[素材] **攻击用例的判据是"三件事同时成立"**：一开始想的是"接口返回 4xx 就算拦住了"。但一个 403 之后数据照样被改了，和一个 200 但什么都没发生，在报告里都叫"失败/成功"，分不清。现在每条负向用例断言三样：**被拒绝、数据零变化、该保护的还在**（canary 文件没被删、审计没多一条）。少一样都不算过。**安全不是"它说了不"，是"说了不之后世界还是原来的样子"。**

[素材] **Agent 层评测必须自己扮演用户，否则一半工具测不到**：查询可以直接调服务层，但删除、导入、改结构都要经过确认卡片——没有真人点按钮，这些工具永远停在 pending。所以写了一个 driver，按 `confirm_hint` 自动回「确认」或「删除 7 条」，按 pending 类型决定续跑还是收尾。它只做 `api.chat()` 做过的事（落结局、清挂起、续跑），**不碰业务逻辑**——driver 里写业务，测的就是 driver 了。顺带一个发现：模型有时先 `ask_user` 再弹删除确认，用例若假定"一定会直接弹确认"，测的就不是产品行为，是某一次的模型选择。

[素材] **假模型不是作弊，是唯一能测"第几次停"的办法**：熔断、超时、压缩这三件事，用真模型测出来的结果每次都不同——这次想 5 轮，下次 8 轮，断言只能写得很松，等于没测。换成假模型：每轮固定返回同一个 tool_call，于是"第 7 次熔断""1.2 秒后超时"变成确定的。**测循环自己的判断时，把不确定的模型换掉；测模型能不能做对时，才需要真模型。**

[素材] **生产库的历史状态会掩盖新库的初始化缺陷**：`_gx_snapshot` 在开发机上一直存在——它是很早以前某次运行留下的，之后每个功能都能正常建快照。但评测跑在全新库上，第一次删列就 `no such table`。同类问题还有：`snapshot.ensure_meta` 只在自己的 `__main__` 里被调用过，`storage.connect` 只建了 storage 自己的三张表。**"我这儿能跑"经常不是代码对，是这台机器上残留了代码没有创建的东西。** 评测第一条价值不是找 bug，是强迫每次从零开始。

[素材] **「RAG 不是工具，是子系统」不是文字游戏**：最容易的实现是给模型一堆文档工具——上传、删除、重建索引、检索。但前三个是**人的动作**：用户上传一份资料，不需要模型理解"上传"这件事；而模型删掉一份语料，是它不该拥有的权力。所以入口拆成两半：文档库页管上传/删除/重建/检索测试（不经过模型），工具层只露 `search_documents` 一个动作。**一个子系统该露给模型几个动作，取决于"哪些动作需要判断"，不是"哪些动作存在"。**

[素材] **切片是真数据，索引是派生数据**：把原文、向量、FAISS 索引捆在一起，删一份文档就要同时删三处；跨存储没有事务，迟早出现"文档删了、索引还能捞出来"。现在写只写 SQLite（一个事务），FAISS 在内存里、数据变更后整个重建。**真源只能有一个，其余都必须是"能重算的"。** 这条判据也让"索引坏了怎么办"有了标准答案：重建，不修。

[素材] **文档库用 `_gx_` 前缀，是因为它不是数据源**：文档也是"内容"，很容易顺手建成 `documents` 业务表——然后数据字典页、导出、垃圾桶、闸门白名单里全多出一类不该碰的东西，模型甚至会尝试对文档表写 SQL。语料和表是两种资产：表回答"有多少、是什么"，语料回答"哪段话说过"。**不同的东西不该共用一个命名空间，哪怕它们都"能查"。**

[素材] **产物默认不进语料，收进去要复制**：`write_document` 写完的文件是交付物，用户可能只是要下载；自动收进文档库会让语料被自己的输出污染，检索时反复命中自己刚写的东西。但用户明确说「收进文档库」时，又**不能把产物搬走**——搬走之后侧栏产物点开就是空的。所以 `to_library` 是显式开关，实现是复制：**一份文件有两个身份时，两个位置都得留；"移动"只适合身份唯一的东西。**

[素材] **Word 预览不引 mammoth，是一次有意降级**：浏览器不内嵌渲染 docx，前端引 mammoth 能保真，但那是 300KB vendor + 一条新的渲染链 + 一套要跟着 Word 样式走的 CSS。现在的做法是后端用 python-docx 把文档摊成"标题 / 段落 / 表格"三类块，前端按页面样式画。**丢掉的是字体字号行距，留下的是内容结构。** 判据是"预览要回答什么问题"：用户点开产物，要确认的是"这份文件写的是不是我要的"，不是"排版和 Word 里一模一样"。样式保真该交给下载后用 Word 打开。

[素材] **权重随包，但不进版本库**：设计说 embedding 要随包（用户第一次检索不该等下载），但 91MB 二进制每 clone 一次都要背。两件事拆开：**交付物里必须有，版本库里不必有。** `models/` 进 gitignore，`scripts/fetch_model.py` 负责准备，打包脚本把它打进去。判断一个文件该不该进库，不看"运行时需不需要"，看"它是不是代码/能不能用代码重新得到"。

[素材] **文档也软删，因为用户对"删除"的直觉只有一套**：语料删错了同样致命，而"表里的行能捞回来、文档删了就没了"会让用户在同一张页面上遇到两种删除语义。现在文档进回收站，检索和列表立即过滤，保留期到了才物理删切片和原文件。**资产可以分很多类，但"删除"这个动作的后果不该分类。**

[素材] **文档操作也进审计**：上传、删除、恢复、清理看起来是"管理语料"，不是"改业务数据"；但对用户来说，这些都是他做过的写操作。审计表里没有它们，就意味着"我什么时候删了那份制度"永远查不到。**判断一个动作要不要留凭据，不看它改的是哪张表，看它改的是不是用户的东西。**

[素材] **扫描件不该由"有没有 OCR 引擎"决定，而该由"模型认不认图片"决定**：本地 OCR 要装引擎、中文识别质量另说；而用户手上的多模态模型本来就能读图。所以路径是：没有文字层 → 页面转 PNG → 交给当前模型。能力清单里加 `vision`，不认就在发请求前拦——**服务端返回的 400 通常只写 unsupported content，用户看不出是"这个模型不支持图片"；能提前判断的，就别让用户去猜报错。** 报错要说人话：「您当前使用的模型没有图片识别能力，无法识别扫描件PDF」。

[素材] **数值参数的位置，取决于"谁会为它打开设置页"**：分块大小、重叠、top_k、相关度门槛，是调检索质量的人才会碰的东西；普通用户打开设置页是想改模型、改保留期。所以这五个数值放开发者模式，不占普通视图。**参数放哪一组，不是按后端模块，而是按"用户为了什么打开这一页"。** 这和当初把设置页按用户找法重分组是同一条账。

[素材] **reranker 的接口要有"没有权重"的正确答案**：如果没下载权重就报错，那这个接口等于强制用户为质量增强付 584MB。现在没有权重时原样返回向量排序，链路完整；有权重才精排。**"可选增强"的实现里必须包含"不装它也能跑"的那条分支，否则它就不是可选的。**

[素材] **评测的顺序依赖，往往藏在"启动副作用"里**：扫描件用例单独跑报 400、全量跑却 200——因为前面 XSS 用例起过一次 uvicorn，lifespan 把真实 LLM 塞进了 `api._state`，后面的 API 就"有视觉能力"了。修法是每条用例前把 `_state["llm"]` 清空。**评测用例之间共享进程时，任何"启动时初始化一次"的全局状态都是隐式依赖；要么显式重置，要么每条用例一个进程。** 这次是顺序变了结果才变，很难靠单跑发现。

[素材] **review 抓到的 bug，评测往往抓不到**：评测看的是"功能对不对、攻击扛不扛得住"，而 review 这次抓到的是**集成点**——async 路由里同步跑完整入库会冻住事件循环（功能测试全绿，因为测试是串行的）、`final` 事件从 `raw` 取产物而 `gx_tools` 里根本没有 `raw`（前端从 SSE 自己收集，所以界面看不出）、mock 模型没有 client 却会走视觉分支（只有"没填 key 还传扫描件"这一种组合）。**评测验证行为，review 验证组合。** 两件事不能互相替代。

[素材] **"没有下载入口"比"给一个下不了的入口"诚实**：reranker 的接口留好了，但查过之后发现 `gte-multilingual-reranker-base` 没有公开的 ONNX 导出（原仓库是 safetensors，Xenova 也没转）。这时候在下载脚本里加一个 `--reranker` 只是让人以为能一键启用，实际 404。所以改成：接口保留、没有权重时原样返回，文档写清"要精排得自己用 optimum 导出"。**一个功能的"可选"，应该由真实可用的准备路径支撑，而不是由参数名支撑。**

[素材] **「能枚举一张表」不等于「能按软删表去读它」**：`list_tables()` 会把用户手工建的表也列出来（这是对的，不列就永远发现不了），但下游很多地方默认每张业务表都有一张 `xxx_all` 底表——启动清理、概览行数、恢复页读数、数据字典的 `real_table`。`repair()` 只会给**有主键**的裸表补保护，无主键的会被 skip，于是那张表一直裸着；下一次启动，清理对它执行 `SELECT ... FROM xxx_all`，`OperationalError` 从 lifespan 冒出来，整个应用起不来。修法不是在每个调用点再写一次判断，而是把"业务名 → 实际存数据的表"收成一个入口 `physical_table()`：有 `_all` 用它，没有就用表自己。**枚举回答"库里有什么"，访问还要回答"它长什么样"；把这两个问题混成一个，就会在"用户绕过系统"的路径上炸。**

[素材] **示例不是文档，是行为**：给模型的工具描述里写「例如'所有 web 类项目'、'已下证的项目'」，给用户的空态写「试试把已下证的项目导成 Excel」——这些字不是注释，模型会照着它理解这张表，用户会照着它理解这个产品。测试数据（软著表的项目名、下证状态）一旦进了运行时文案，产品就假装自己只服务那一个业务。清理时改成「所有已完成的记录」「某个分类下的记录」这类与表无关的例子。**判据：示例也应该对"任何一张表"成立；只在某张表上成立的例子，是测试夹具漏进了产品。**

[素材] **死键的来源不是"忘了删"，是"改界面时只搬新、不扫旧"**：左栏从双 tab（会话/轨迹）改成常驻会话列表后，`tabSessions` / `tabTrace` 没有调用方了；轨迹页的统计文案换了写法，`traceRounds` / `toolTime` / `statOk` 也留在了表里。更隐蔽的是另一类：键还在表里，界面却把同一句话硬编码在组件里（`inputPlaceholder`、`thinkRound`、`filesCount`）。前者删掉没风险；后者说明"文案集中"只做了一半。**清理死键容易，难的是承认那张表并不是唯一入口——下次改文案仍要全局搜一遍。**
